El punto de partida

Dos servicios que no se conocen

Sin microservicios

Un solo proyecto, una base de datos, un JOIN y listo.

Funciona. Es rápido de construir. Y cuando un equipo quiere publicar su parte de forma independiente, no hay por dónde empezar.

Con microservicios

Dos procesos, dos bases. Y entonces surge la pregunta que no tiene atajo: ¿cómo sabe el uno que el otro tiene ese dato?

La respuesta obvia —"que lo pregunte"— es exactamente el diseño de este proyecto. Y resulta que no es una solución improvisada: es un patrón real, con un nombre (service client o API Gateway), con sus ventajas y con sus costes.

Lo que sigue es ese patrón, construido entero, midiendo lo que cuesta.

El flujo · fase 1

Inicio de sesión, una vez

  1. 1
    El cliente manda email y contraseña a POST /api/tokens.
  2. 2
    El user-service verifica el hash de la contraseña y emite un token opaco: 64 caracteres hexadecimales aleatorios, con expires_at a 60 minutos.
  3. 3
    En la tabla solo se guarda su SHA-256. Si alguien lee la base de datos, no puede suplantar a nadie.
  4. 4
    El token en claro viaja una única vez, en la respuesta 201.
SHA-256 para el token, PBKDF2 para la contraseña: el token no es una contraseña que alguien pueda escoger — son 32 bytes de secrets.token_hex, no hay espacio de búsqueda que recorrer. La contraseña sí la elige el usuario, y ahí el hash lento (PBKDF2, de la stdlib, con hmac.compare_digest) es el que importa. Todo sin dependencias nuevas.
El flujo · fase 2

Cada request posterior

  1. 1
    El cliente envía Authorization: Bearer <token>.
  2. 2
    El task-service no puede validarlo: la tabla de tokens no es suya. Así que se lo reenvía al user-service.
  3. 3
    GET /api/user responde 200 {id, name, email} o 401. Es la introspección de tokens de un identity provider.
  4. 4
    El user_id de la tarea sale de la identidad, nunca del cuerpo del request.
  5. 5
    Para una tarea concreta se comprueba la propiedad: si no es tuya, 403.
Y si el user-service está caído, el task-service devuelve 503 en todo. Nadie puede autenticarse. Eso no es un defecto de implementación: es el precio, visible y medible, de no duplicar el estado de identidad.
La pieza clave

Toda la frontera de red vive en un sitio

# task-service/app/user_service_client.py — el único archivo que sabe que existe HTTP
def verify_token(token: str) -> dict:
    try:
        r = _http_get(USER_SERVICE_URL + "/api/user",
                     {"Authorization": "Bearer " + token})
    except (httpx2.ConnectError, httpx2.ConnectTimeout):
        raise HTTPException(503, "user-service no está en pie …")

    if r.status_code == 401:
        raise HTTPException(401, "Token inválido o expirado")
    if r.status_code != 200:
        raise HTTPException(502, "Respuesta inesperada del user-service")
    return r.json()

def _http_get(url, headers):          # el seam: los tests lo sustituyen
    with httpx2.Client(timeout=2) as http:
        return http.get(url, headers=headers)
Los endpoints no saben nada del tema. No hay URLs, ni timeouts, ni códigos de error del peer fuera de este archivo. Es el patrón de un API Gateway: tratar al otro microservicio como si fuera una función local.
La distinción que importa: 401 es "este token no vale" y baja como 401 propio. El peer caído es 503, con el comando para levantarlo; una respuesta inesperada es 502. Confundir "vuelve a loguearte" con "el sistema está roto" es el error clásico.

Anti-enumeración

Contraseña equivocada y email fantasma devuelven exactamente lo mismo. Un atacante no puede usar el endpoint para adivinar qué correos están registrados. Verificado con dos curl en el E2E: las dos respuestas son idénticas.

El header malformado no viaja

Si el header no es Bearer <token>, se rechaza con 401 en deps.py sin llamar a la red. El malformado es problema del cliente, no del IdP.

Trampa de sqlite: la base no conserva el tzinfo. En las columnas, las fechas se guardan naive en UTC; el Z de la respuesta ISO 8601 se añade al final, con .replace(tzinfo=UTC), justo antes de serializar.
La lección

Un bug de diseño que la auth silenció

Antes

# el cliente afirmaba de quién era la tarea
user_id = payload["user_id"]

if find_user(user_id) is None:
    raise HTTPException(422, "usuario inexistente")

task = Task(title=payload["title"],
            user_id=user_id)

La validación solo comprobaba que el usuario existiera — no que quien llamara fuera ese usuario.

Ahora

@router.post("/api/tasks", status_code=201)
def create(payload: TaskCreate,
           user: dict = Depends(get_current_user)):
    return Task(title=payload.title,
                user_id=user["id"])

Una validación de existencia no es una autorización. Con autenticación, el user_id dejó de ser un dato que el cliente afirma y pasó a ser una identidad que el sistema resuelve.

Y ninguna validación de user_id quedó en el código. No es un descuido: la dependencia ya preguntó lo mismo por el mismo canal. Preguntarlo otra vez era pagar la latencia otra vez para obtener la misma respuesta. 
$ curl -X POST .../api/tasks -H "Authorization: Bearer $T" \
       -d '{"title":"Zapatos de boda","user_id":99}'
{"title":"Zapatos de boda","user_id":1,...}   # el 99 se descartó
Lo que salió mal

Tres errores que nadie encontró leyendo el código

Tres tests rojos por un reloj

Fechas aware comparadas con fechas naive: el test dio 3 failed, 4 passed. sqlite no conserva el tzinfo, así que la comparación de caducidad explotaba por mezcla de relojes.

→ Columnas naive en UTC y el Z solo al responder.

El DELETE en 401

Un parámetro authorization: str = None sin Header() — FastAPI lo leyó como query param. El header nunca llegaba y el DELETE respondía 401 siempre.

→ En FastAPI nada es implícito: el header se declara.

El test que expiró otra fila

first() traía el token de otro test anterior. El test expiraba una fila cualquiera y el aserto pasaba o fallaba por casualidad.

→ El test expira la fila del token que realmente usa, buscando por su hash.

Los tres los encontraron los tests o el curl del E2E, no la lectura. Dos de ellos además solo aparecían en el camino infeliz: token expirado y header ausente.

Un test del task-service no sabe que existe HTTP. La frontera está stubbeada, la identidad viene de un override: corren en milisegundos y sin un solo socket abierto.
Los tres caminos de la frontera se prueban a mano. 401 del IdP, ConnectError y status inesperado: cada uno con su stub y su status esperado (401, 503, 502).

Criterio

Decisiones y el porqué

DecisiónAlternativa descartadaPor qué
Token opaco + SHA-256 JWT Un único dueño del estado de identidad y revocación inmediata — probada: el DELETE responde 204 y el token muere al instante en los dos servicios.
PBKDF2 de la stdlib passlib / argon2-cffi Capítulo de fundamentos: cero dependencias nativas para el hashing, y hmac.compare_digest para la comparación.
uv por servicio Workspace / monorepo Cada servicio su pyproject.toml y su .venv — el paralelo exacto de un composer install por servicio.
SQLite MySQL / PostgreSQL Dos archivos, dos procesos, cero infraestructura. El aislamiento del ejercicio se demuestra igual.
Tests con overrides Servers en pie / respx Herméticos y sin red real: la identidad por dependency_overrides, el IdP por monkeypatch. Un test no depende de otro proceso.
Columnas naive en UTC Datetime aware en columnas sqlite no conserva tzinfo; guardar aware es pedir comparaciones rotas. El Z es un asunto de la respuesta, no del almacenamiento.
Hacia dónde

El siguiente paso no es RabbitMQ

Primero — barata y evita incidentes

  1. X-Request-Id propagado + métricas
  2. Circuit breaker (de 2 s de espera a ~0 ms)
  3. Refresh tokens
  4. API versioning
  5. Contratos de consumidor en CI

Después — solo si el punto 2 duele

  1. RabbitMQ (de síncrono a asíncrono)
  2. Docker + health checks
  3. Gateway o JWT, si aparece un tercer consumidor
El orden importa: los primeros cinco cuestan horas y evitan incidentes. RabbitMQ puede esperar sin que nadie lo note. Añadirlo antes es infrastructure por adelantado.
El riesgo estructural que queda: los tests stubbean al otro servicio. Si alguien cambia la forma del 401 en el user-service, los tests del task-service seguirán en verde y se rompe en producción. Los contratos de consumidor lo resuelven, y es el paso que más duele no hacer.
