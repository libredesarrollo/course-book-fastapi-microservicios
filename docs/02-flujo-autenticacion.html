Autenticación entre microservicios FastAPI: flujo completo

Resumen: cuando dos servicios no comparten base de datos, el que quiere proteger un recurso no puede validar por su cuenta quién está llamando. La solución más simple y la más honesta es que le pregunte al servicio dueño de la identidad por HTTP. Este artículo implementa exactamente eso con FastAPI, muestra el código completo, y explica lo que cuesta.

Lo construimos sobre un proyecto real de dos servicios: user-service (dueño de los usuarios, autenticador) y task-service (dueño de las tareas). Cada uno con su base de datos sqlite, sin llaves foráneas cruzadas, hablando solo por HTTP. Cada servicio es un proyecto uv independiente, con su propio pyproject.toml y su propio .venv.

1. El problema que resuelve la autenticación

Antes de añadir autenticación, el flujo era "abierto": cualquiera podía crear, editar y borrar cualquier tarea.

$ curl -X POST http://127.0.0.1:8001/api/tasks \
    -H "Content-Type: application/json" \
    -d '{"title":"Tarea maliciosa","user_id":42}'

201 Created   # sin preguntar quién eres

Y más grave: el user_id venía en el cuerpo del request. Una validación por HTTP al user-service solo comprobaría que ese usuario existiera, no que quien llamara fuera ese usuario. Cualquiera podía crear una tarea "de Ana Torres" sin ser Ana.

Eso significa que la validación hace la mitad del trabajo, y la mitad que falta es la importante. La autenticación cierra ese hueco: el user_id deja de ser un dato que el cliente afirma y pasa a ser una identidad que el sistema resuelve.

El punto de partida

# LA FORMA SIN AUTH: el cliente dice quién es, y hay que ir a comprobar que existe
user_id = payload["user_id"]

if find_user(user_id) is None:
    raise HTTPException(422, "El usuario no existe en el sistema")

task = Task(title=payload["title"], user_id=user_id)

El bug de fondo: una validación de existencia no es una autorización. La primera responde "¿este id corresponde a alguien?", la segunda responde "¿tienes derecho a actuar en nombre de ese alguien?". Son preguntas distintas, y esta implementación solo haría la primera. En este proyecto esa versión nunca llegó a existir: el sistema se construyó ya con la lección aprendida de la serie hermana en Laravel, que sí vivió ese bug.

2. La decisión: validar por HTTP o token stateless

El task-service necesita saber quién llama. Pero la tabla de usuarios y de tokens vive en el user-service. Hay dos caminos, y no son equivalentes.

Validar por HTTP (lo que hicimos)Token stateless (JWT)
Dónde se valida El task-service reenvía el token al user-service El task-service verifica la firma en local, sin llamar a nadie
Latencia por request +1 salto de red (~2 ms en local, medido) 0 saltos
Si el user-service cae Nadie puede autenticarse: 503 en todo La API sigue funcionando con normalidad
Revocar un token Trivial: borrar la fila Difícil: el token es válido hasta que expira
Escalado Cada réplica del user-service recibe carga extra Totalmente horizontal

Elegimos validar por HTTP. Es el diseño arquitectónicamente correcto: el estado de identidad tiene un único dueño y nadie lo replica. El costo es explícito y, sobre todo, demostrable en cinco segundos apagando un servicio.

El downside lo conocemos antes de escribir el código: es exactamente lo que un JWT viene a evitar. Lo dejamos así a propósito, y más abajo comparamos las opciones con sus números.

3. El flujo, paso a paso

  LOGIN (una vez)

  Cliente ──POST /api/tokens──▶ user-service ──▶ SELECT en users
      │         {email,           │                INSERT en api_tokens
      │          password}        │◀── token en claro (una sola vez)
      │◀────── 201 + token ───────┘

  CADA REQUEST POSTERIOR

  Cliente ──GET /api/tasks──▶ task-service ──GET /api/user──▶ user-service
      │                        dependencia                      SELECT por
      │                            │                             hash sha256
      │                            │◀──── {id, name, email} ─────┘
      │                            │
      │                            ▼  "¿quién es este token?"
      │                        dict del usuario
      │                            │
      │                            ▼
      │                        db_tasks (user_id = identidad, no input)
      │◀───── 200 / 201 / 401 / 403 ─┘
  1. El cliente manda email y contraseña al user-service.
  2. El user-service verifica el hash de la contraseña y emite un token opaco.
  3. El cliente usa ese token como Authorization: Bearer <token>.
  4. El task-service no puede validarlo (no tiene la tabla), así que se lo reenvía al user-service.
  5. El user-service responde quién es. Si el token no existe o expiró, responde 401.
  6. El task-service recibe esa identidad como dict y sigue.
  7. El user_id sale de ahí. Nunca del cuerpo del request.

4. La tabla api_tokens (solo hashes)

class ApiToken(Base):
    __tablename__ = "api_tokens"

    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)

    # Token opaco: se guarda solo el hash, el crudo sale una vez del login.
    token_hash: Mapped[str] = mapped_column(String(64), unique=True, index=True)
    name: Mapped[str] = mapped_column(String(100), default="api-token")
    expires_at: Mapped[datetime] = mapped_column(DateTime)
    created_at: Mapped[datetime] = mapped_column(DateTime, default=utcnow)

    user: Mapped[User] = relationship(User)

Aquí hay una FK, y está bien: es una integridad interna del user-service con su propia tabla. Lo que no existe son FKs cruzadas hacia tareas.

Hay una diferencia deliberada con la versión Laravel de esta misma serie: aquí expires_at es NOT NULL. Un token sin caducidad sirve para siempre, y eso se hace imposible por esquema, no por convención. El TTL vive en la configuración (60 minutos) y la emisión lo estampa en cada fila.

Emitir el token

def issue_token() -> tuple[str, str]:
    """Devuelve (token crudo, hash para guardar). El crudo viaja una sola vez."""
    token = secrets.token_hex(32)
    return token, hashlib.sha256(token.encode()).hexdigest()

Buscar un token

def authenticate(db: Session, authorization: str | None) -> tuple[User, ApiToken]:
    """¿Quién es este token? La respuesta es 401 ante token inválido o expirado."""
    token = _bearer_token(authorization)
    if token is None:
        raise HTTPException(status_code=401, detail="Token no presentado o malformado")

    row = db.query(ApiToken).filter(ApiToken.token_hash == security.hash_token(token)).first()
    if row is None:
        raise HTTPException(status_code=401, detail="Token inválido o expirado")

    # Token caducado: para el cliente es idéntico a uno inexistente.
    if row.expires_at <= utcnow():
        raise HTTPException(status_code=401, detail="Token inválido o expirado")

    return row.user, row

La consulta es un índice único sobre un hash de 64 caracteres. O sea, O(1) y sin posibilidad práctica de colisión.

Por qué SHA-256 y no bcrypt/Argon2: porque el token no es una contraseña que alguien pueda escoger. Son 32 bytes de secrets.token_hex, sin espacio de búsqueda que recorrer. El atacante tendría que adivinar el token entero; hashear es solo para que una fuga de la base de datos no sirva. Con la contraseña elegida por el usuario, el ataque de fuerza bruta sí es realista y ahí sí toca un hash lento: esta versión usa PBKDF2 de la biblioteca estándar (100 000 iteraciones, con hmac.compare_digest), cero dependencias.

5. La dependencia del task-service

Este es el corazón del asunto. El task-service recibe un token que no puede validar, así que lo reenvía. En FastAPI el "middleware" de Laravel es una dependencia: FastAPI la resuelve antes de entrar al handler, en cada endpoint que la declare.

def get_current_user(
    authorization: str | None = Header(default=None),
) -> dict[str, Any]:
    parts = authorization.split(" ", 1) if authorization else []
    if len(parts) != 2 or parts[0] != "Bearer" or not parts[1].strip():
        # Header ausente o malformado: problema del cliente, se rechaza aquí
        # sin llamar a la red.
        raise HTTPException(status_code=401, detail="Token no presentado o malformado")
    return verify_token(parts[1].strip())

Y todo lo que sabe que existe la red vive en un solo archivo:

# app/user_service_client.py
def _http_get(url: str, headers: dict[str, str]) -> httpx2.Response:
    with httpx2.Client(timeout=config.HTTP_TIMEOUT_SECONDS) as http:
        return http.get(url, headers=headers)


def verify_token(token: str) -> dict[str, Any]:
    """¿Quién es este token? Toda la frontera de red vive en este archivo:
    los demás módulos reciben el dict del usuario como si fuera local."""
    try:
        resp = _http_get(
            f"{config.USER_SERVICE_URL}/api/user",
            headers={"Authorization": f"Bearer {token}"},
        )
    except (httpx2.ConnectError, httpx2.ConnectTimeout):
        # Es un fallo de infraestructura, no de identidad: el cliente merece
        # saber qué servicio falta y cómo levantarlo.
        raise HTTPException(
            status_code=503,
            detail=(
                "user-service no está en pie (se esperaba "
                f"{config.USER_SERVICE_URL}); levántalo con "
                "`uv run uvicorn app.main:app --port 8000` en user-service/"
            ),
        )

    if resp.status_code == 200:
        user = resp.json()
        # El cliente del IdP devuelve {id, name, email}; nada más entra aquí.
        return {"id": int(user["id"]), "name": str(user["name"]), "email": str(user["email"])}

    if resp.status_code == 401:
        # La distinción que importa: 401 NO es un fallo del servicio, es
        # identidad inválida del token presentado.
        raise HTTPException(status_code=401, detail="Token inválido o expirado")

    raise HTTPException(
        status_code=502,
        detail=f"Respuesta inesperada del user-service (HTTP {resp.status_code})",
    )

Fíjate en la distinción: 401 significa "identidad inválida" y baja como 401 propio. Una caída de conexión es 503, con el comando exacto para levantar lo que falta. Cualquier otro status es un problema del peer y se traduce a 502. Confundir esos casos es un bug clásico: termina tratando "tu token venció" como "el servidor se cayó".

Una decisión con nombre: la función _http_get existe para que los tests la sustituyan. Ningún test de este proyecto toca la red: el IdP se stubbea cambiando esa función por otra que responde el status que toca. Es el equivalente exacto de Http::fake() en Laravel.

El login, para completar el cuadro

@router.post("/tokens", response_model=TokenIssued, status_code=201)
def issue_token(payload: TokenRequest, db: Session = Depends(get_db)) -> TokenIssued:
    user = db.query(User).filter(User.email == payload.email).first()

    # Mismo mensaje y mismo status para "no existe" y "contraseña mala": si no,
    # esta respuesta sirve para enumerar qué emails están dados de alta.
    if user is None or not security.verify_password(payload.password, user.password):
        raise HTTPException(status_code=401, detail="Credenciales inválidas")

    token, token_hash = security.issue_token()
    expires_at = security.expiry()
    row = ApiToken(
        user_id=user.id,
        token_hash=token_hash,
        name=payload.device_name or "api-token",
        expires_at=expires_at,
    )
    db.add(row)
    db.commit()

    return TokenIssued(
        token=token,
        token_type="Bearer",
        expires_at=expires_at.replace(tzinfo=UTC),
        user=UserInfo.model_validate(user),
    )

Y el logout que revoca de verdad

@router.delete("/tokens", status_code=204)
def revoke(
    authorization: str | None = Header(default=None),
    db: Session = Depends(get_db),
) -> None:
    user, row = authenticate(db, authorization)
    db.query(ApiToken).filter(ApiToken.id == row.id).delete()
    db.commit()

Muchas implementaciones olvidan este paso y el "cerrar sesión" solo borra una cookie del lado cliente: el token sigue sirviendo hasta que expira. Borrar la fila es una revocación real e inmediata, y es el trade-off que compra el token opaco. Verificado en el E2E: el DELETE responde 204 y el mismo token, usado un segundo después a través del task-service, recibe 401.

6. De dónde sale el user_id, y por qué ya no se valida

Aquí está el cambio de fondo, y conviene mirarlo de cerca porque es la lección del ejercicio.

@router.post("/tasks", response_model=TaskOut, status_code=201)
def create_task(
    payload: TaskCreate,
    current_user: dict[str, Any] = Depends(get_current_user),
    db: Session = Depends(get_db),
) -> Task:
    task = Task(
        title=payload.title,
        status=normalize_status(payload.status, STATUS_PENDING),
        # El dueño lo pone el sistema: el cliente no manda user_id.
        user_id=current_user["id"],
    )
    db.add(task)
    db.commit()
    db.refresh(task)
    return task

Una versión sin auth llamaría al user-service por HTTP para comprobar que el user_id del payload fuera válido. Esa llamada no existe, y no es un descuido: es que sería redundante.

La dependencia acaba de confirmar por HTTP que ese mismo usuario existe. Preguntarlo otra vez sería pagar la latencia otra vez para obtener la misma respuesta. La validación y la autenticación hacen el mismo trabajo; con autenticación, la validación quedó absorbida.

Y el user_id ni siquiera existe en el schema de entrada: TaskCreate valida title y status. Si un cliente manda user_id a propósito, pydantic lo descarta en silencio.

$ curl -X POST .../api/tasks -d '{"title":"Zapatos de boda","user_id":99}'
{"title":"Zapatos de boda","user_id":1, ...}   [201]   # el 99 se ignoró

Y las tareas de otros

def find_owned(task_id: int, current_user: dict[str, Any], db: Session) -> Task:
    task = db.get(Task, task_id)
    if task is None:
        raise HTTPException(status_code=404, detail="Tarea no encontrada")
    if task.user_id != current_user["id"]:
        raise HTTPException(status_code=403, detail="No es tu tarea")
    return task

El user_id almacenado sí se sigue usando, pero para algo distinto: para comprobar propiedad, no para validar identidad. Esa distinción es el corazón del cambio.

Un detalle que FastAPI regala gratis: las dependencias se resuelven antes que el handler, así que un anónimo que pida /api/tasks/1 recibe 401 y nunca llega a tocar la base de datos. En la versión Laravel de esta serie, el route model binding corría antes del middleware de auth y filtraba qué ids existían (404 vs 403 para un dato que no debía conocer). Aquí el orden correcto viene de fábrica: primero identidad, después existencia.

7. ¿Y la sesión web?

La versión Laravel de este capítulo tenía una interfaz web con formulario de login que guardaba el token en la sesión del task-service. Esta versión no la tiene, y es una decisión de alcance, no un descuido: el capítulo 1 en FastAPI es API puro, y el cliente es siempre un programa (curl, test, SPA) que manda el header.

Lo que sí conviene quedarse del diseño web es la regla que lo ordenaba: una sola fuente de identidad. Allí el middleware aceptaba el header o la sesión, y en ambos casos la validación ocurría siempre en el user-service. Aquí solo existe el header, así que la regla se cumple por defecto.

Si algún día este proyecto crece una UI, el camino es el mismo que en Laravel: el task-service canjea credenciales por un token, lo guarda en su sesión y lo reenvía en cada request. El día que eso duela, es la señal de que toca la opción C de la sección 13 (login centralizado).

8. Cuatro errores reales que aparecieron

Ninguno se detectó leyendo el código: los encontraron los tests y el curl del E2E.

8.1 Tres tests rojos por un reloj

La primera versión comparaba fechas aware contra fechas naive: la suite dio 3 failed, 4 passed. La causa de fondo es sqlite, que no conserva el tzinfo: guardar datetimes aware en columnas y compararlos con now() aware es pedir comparaciones rotas.

# la comparación de caducidad explotaba mezclando relojes
row.expires_at <= utcnow()   # naive vs aware -> TypeError en algunos caminos

La solución fue una regla, no un parche: en las columnas todo se guarda naive en UTC (el reloj del sistema convertido con datetime.now(UTC).replace(tzinfo=None)), y el Z de la respuesta ISO 8601 se añade al final, con .replace(tzinfo=UTC), justo antes de serializar. El "aware" es un asunto de la respuesta al cliente, no del almacenamiento.

8.2 Un DELETE que respondía 401 siempre

Un parámetro authorization: str = None sin Header() — FastAPI lo leyó como query param. El header nunca llegaba a la función y el DELETE respondía 401 siempre, con el endpoint funcionando "bien" para los caminos que pasaban el header por otros medios en los tests.

La lección de FastAPI: nada es implícito. Un query param y un header se declaran igual de explícito, y la diferencia es una sola palabra (Header()) que decide de dónde viene el dato. La prueba que lo encontró pedía exactamente el mensaje del 401 propio.

8.3 El test que expiró otra fila

Un test de caducidad hacía db.query(ApiToken).first() y le restaba un minuto al expires_at. Con la base de datos compartida entre tests, first() traía el token de otro test anterior: el test expiraba una fila cualquiera y el aserto pasaba o fallaba por casualidad.

La solución: el test busca la fila por el hash del token que realmente usa — hashlib.sha256(token.encode()).hexdigest() — y expira esa. Y de regalo, una fixture autouse que borra los overrides de identidad al empezar cada test, para que nadie arrastre la identidad del anterior.

8.4 El esquema prefabricado que se comía el contrato

security = HTTPBearer()   # detalle "oficial" de FastAPI

def get_current_user(credentials = Depends(security)) -> dict:
    token = credentials.credentials
    ...

La versión con HTTPBearer ahorra tres líneas y pierde el contrato: ante un header ausente o malformado responde 401 "Not authenticated", su mensaje genérico, no el nuestro. Además no puede rechazar el malformado sin red: no sabe que la frontera existe. El test que verifica "401 con nuestro mensaje y cero llamadas de red" lo detectó de inmediato.

La solución: la dependencia propia de la sección 5, que son unas diez líneas. En un capítulo sobre fronteras, el detalle donde se gobierna la frontera no se delega en un prefabricado que no sabe nada de ella.

La distinción importante es la fila 2 contra la 4: "no sé quién eres" y "no puedo preguntarte quién eres" son dos problemas distintos y merecen respuestas distintas. Confundirlos convierte un simple "vuelve a loguearte" en un "el sistema está roto".

Y hay una regla de cortesía que no es decoración: el 503 dice qué servicio falta y el comando exacto para levantarlo. Sin eso, el desarrollador que recibe el 503 ve "el sistema está caído" y tiene que adivinar cuál de las dos piezas.

Todos los pasos de esta lista son los del E2E real de este proyecto, corridos con los dos servidores en pie y medidos con curl -w "%{time_total}".

11. El precio: latencia y disponibilidad

Esta es la parte que conviene medir, no suponer. Números reales de este proyecto, con los dos servicios en pie en localhost (mediana de tres corridas):

PeticiónLatenciaQué incluye
POST /api/tokens (login)~10 msverificación PBKDF2 (100 000 iteraciones) + INSERT
GET /api/user (introspección directa)~2 msSELECT por hash en el IdP
GET /api/tasks (vía frontera)~3-6 msla introspección de arriba, más la consulta propia del task-service
SIN autenticación (antes)          CON autenticación por HTTP (ahora)

Cliente ──── ~3ms ──▶ task-svc     Cliente ─── ~4ms ───▶ task-svc
                                    ─── ~2ms ───▶ user-svc
Total ≈ 3 ms                        Total ≈ 4-6 ms (introspección incluida)

El salto de red cuesta aquí unos 2 ms: es visible, y es justo lo que un JWT eliminaría. La honestidad del diseño consiste en mostrar ese número en la tabla en lugar de teorizarlo.

La cascada de disponibilidad

La disponibilidad del task-service pasa a depender de la del user-service de forma directa. Si el user-service está caído:

  • El login falla (503).
  • La API devuelve 503 en todo, incluso para lecturas.
  • Cada respuesta 503 dice qué servicio falta y el comando para levantarlo.

Con la conexión rechazada el 503 llega en ~4 ms (el SO dice "nadie escucha en ese puerto" al instante). El escenario caro es otro: el user-service colgado (acepta conexiones y no responde) haría esperar el timeout completo, que aquí es de 2 segundos por request. Un circuit breaker lo convertiría en un fallo inmediato; está en el roadmap, no en este capítulo.

Y lo que se ganó a cambio

  • El estado de identidad tiene un solo dueño. Nadie lo replica ni lo cachea.
  • Revocar es borrar una fila. Inmediato, sin esperar expiraciones — probado en el paso 6 del E2E.
  • El user-service puede aplicar sus propias reglas (TTL, anti-enumeración, rate limiting futuro) sin avisar a nadie.

12. Las alternativas y cuándo tienen sentido

Token stateless (JWT)

El user-service firma un JWT y el task-service verifica la firma en local, sin llamada de red. Resuelve exactamente el problema del apartado anterior.

A cambio:

  • Revocar se vuelve difícil. Hasta que expira, el token vale, lo borres o no.
  • El payload no es secreto: es base64, no cifrado.
  • El reloj de los servicios puede desincronizarse y romper nbf / exp.
  • Si ya tienes base de datos, la tabla de revocación es una fila más.

Cuándo tiene sentido: cuando hay terceros que deben validar el token sin poder consultar tu base de datos. O cuando el user-service es el cuello de botella real.

mTLS o API Gateway

La respuesta de producción para tráfico interno. El servicio se identifica con un certificado (mTLS) o con un token de servicio emitido por un gateway con client_credentials de OAuth2: vida corta, audiencia específica, revocable.

Ventaja sobre todo lo anterior: separa la identidad del servicio de la identidad del usuario. En el diseño de este artículo, el task-service reenvía el token de una persona en cada request; con mTLS, lo identifica el certificado del servidor y el token del usuario viaja dentro.

EnfoqueLatenciaRevocaciónComplejidadCuándo
Validar por HTTP1 saltoInmediataBajaAprendiendo, 2-3 servicios, monolito modular
JWT0 saltosComplejaMediaMuchos servicios, terceros validando
mTLS / Gateway0 saltos extra*Por rotaciónAltaProducción seria, Kubernetes

* mTLS no añade saltos de red, pero sí handshake TLS y gestión de certificados, que es donde está su coste real.

El orden sensato es empezar por validar por HTTP porque es la opción que te deja ver el problema, y saltar a la siguiente cuando ese problema te esté doliendo. Montar mTLS antes de tener dos servicios es pagar una factura que todavía no te llegó.

13. ¿Y si hay un tercer microservicio?

Metamos un tags-service: mismo patrón que tasks, su propia base de datos, hablando con el user-service. La pregunta es si hay que volver a escribir el cliente y la dependencia de tasks, y qué alternativas existen.

Antes de listar opciones conviene mirar qué es realmente lo que se duplicaría, porque no es lo que parece. En el task-service hay dos piezas:

# task-service
deps.py                   -> lee el header, rechaza el malformado, llama a la frontera
user_service_client.py    -> verify_token(): la frontera de red (401 / 503 / 502)

Ninguna de las dos tiene nada de dominio de tareas. Su trabajo es: "soy un cliente del proveedor de identidad, dime quién es este token". Eso es un rol de OAuth client, no de servicio de tareas.

La observación que ordena el debate: hay dos piezas de naturaleza muy distinta.

  • La dependencia (~10 líneas) es la frontera de seguridad. Es pequeña, casi no cambia, y su código es el mismo en cualquier servicio.
  • El cliente del IdP (~50 líneas) lleva URL, timeout y la clasificación de errores. Es el que se va a duplicar.

La pregunta "¿duplico el cliente?" en realidad es "¿cuántos sitios dejamos que implementen el baile de OAuth client?"

Opción A — Duplicar en cada servicio

Copiar los dos módulos a tags-service tal cual. Es lo que haría cualquiera por defecto, y no es una mala decisión.

A favor: cada servicio se despliega y se rompe de forma independiente. Ningún servicio depende del release de otro.

En contra: N copias. Si mañana añades un circuit breaker al cliente, o cambias el mensaje del 503, tienes que acordarte de los N. El coste no es el tamaño del archivo: es el número de sitios donde puede olvidarse alguien de arreglar un fallo de seguridad.

Cuándo: con dos o tres servicios. Este proyecto tiene dos, y por eso la opción A es razonable hoy.

Opción B — Extraer a un paquete local compartido

Un paquete local, referenciado como path dependency de uv en el pyproject.toml de cada servicio, que exporta la dependencia, el cliente y los tipos.

# pyproject.toml de cada servicio
[tool.uv.sources]
microservice-kit = { path = "../packages/microservice-kit" }

dependencies = [
    "fastapi>=0.162",
    "microservice-kit",
]

Cada servicio recibe el código y puede extenderlo si necesita. Una sola fuente de verdad, y el bug de seguridad se arregla una vez.

A favor: una copia, versionable, y cada servicio puede ajustar lo suyo sin romper a los demás.

En contra, y es importante: acopla los ciclos de release. Un error en el paquete rompe los tres servicios a la vez, y cada servicio queda clavado en la versión que le funciona. Además aparece el problema clásico de "este servicio necesita un parche del paquete, y ya hay tres en producción". Es un coste que no se ve hasta el cuarto servicio.

Cuándo: cuando ya tienes más de tres o cuatro servicios del mismo equipo y despliegan juntos. Antes de eso es infraestructura por adelantado.

Opción C — Login centralizado en el user-service

El user-service aloja el formulario, recibe la contraseña, emite el token y devuelve al cliente a la app que lo pidió. El task-service y el tags-service no tienen ningún código de login: solo la dependencia.

Cliente ──▶ /login (en user-service)
              │
              ├─ POST /api/tokens  (allí mismo, sin salir del servicio)
              │
              └─▶ redirige a http://tasks.app.local/tasks  + el token

El argumento fuerte, y es contraintuitivo: esto no añade acoplamiento nuevo. Todos los servicios ya dependen del user-service para validar cualquier request, así que mover el login allí no crea ninguna dependencia que antes no existiera. Lo que hace es eliminar código duplicado.

A favor: una sola UX de login en toda la organización. Y cuando llegue MFA, passkeys o "login con Google", se implementa una vez y todos los servicios lo heredan sin tocar una línea.

En contra: el user-service deja de ser solo un servicio de datos y se convierte en algo con cara de aplicación. Y aparece un problema serio de transporte, que es el siguiente punto.

El detalle que se cuela aquí: cómo cruza el token

El token tiene que volver del user-service al task-service de alguna manera, y cada opción tiene un problema distinto:

MétodoCómo funcionaRiesgo
Query string
?token=...		 El redirect más simple El token queda en los logs del servidor, en el historial del navegador y en la cabecera Referer de la siguiente página. No usarlo.
Fragment
#token=...		 La parte tras el # nunca viaja al servidor Requiere JavaScript para leerlo y guardarlo. Funciona, pero mete JS en el camino crítico del login.
Cookie de dominio padre
.app.local		 El user-service deja la cookie y todos los servicios la leen Exige que las apps compartan dominio padre. Y en realidad, ¿para qué volver al login si la cookie ya autentica a todas?
form_post
(estándar OIDC)		 El user-service devuelve un formulario auto-enviado por POST Es el más correcto para el flujo servidor-a-servidor, y el más inusual de montar.

La observación: en cuanto piensas en cómo transportar el token entre servicios, descubres que la opción C empuja el problema hacia una respuesta más interesante, y por eso termina siendo la opción D.

Opción D — API Gateway / BFF en el borde

Un componente delante de todos los servicios hace el login una vez y entrega a cada servicio una identidad ya resuelta en una cabecera. Los servicios dejan de hablar de autenticación por completo.

Cliente ──▶ Gateway ──X-Authenticated-User: {"id":1,...}──▶ task-service
                │
                ├─▶ tags-service
                └─▶ user-service

Los servicios ya NO llaman al user-service en cada request.

A favor: elimina el salto de red por request (el problema de la sección 11, resuelto de raíz), la política queda en un solo sitio, y añadir un servicio nuevo no requiere tocar auth en absoluto.

En contra, y son graves:

  • La cabecera se puede falsificar. Si alguien alcanza task-service saltándose el gateway, puede mandar X-Authenticated-User a mano y ser Ana. La red interna tiene que estar cerrada y verificada, o la cabecera tiene que ir firmada.
  • El gateway pasa a ser infraestructura crítica: si se cae, no entra nadie.
  • Introduce un componente más que operar, con su propio despliegue, sus logs y sus versiones.

Cuándo: en producción con Kubernetes, cuando el número de servicios hace que la latencia por request importe de verdad. No antes.

Opción E — Que el cliente haga el login

Una SPA o app móvil habla solo con el user-service (o el gateway) para autenticarse, guarda el token en su propio almacenamiento, y lo envía en cada request. Ningún servicio tiene formulario de login.

A favor: los servicios quedan sin una línea de código de UI de autenticación. Es el patrón normal en mobile, y de hecho es lo que este proyecto ya es: el "cliente" de la sección 10 es exactamente eso.

En contra: necesitas ese cliente. Y el token vive en el navegador, lo que reabre la discusión entera de XSS vs httpOnly cookie.

Comparación

Opción Código de login por servicio Saltos de red por request Riesgo principal Cuándo
A. Duplicar Sí, N copias 1 Olvidarse de arreglar un fallo en los N sitios 2-3 servicios
B. Paquete No, se hereda 1 Acoplar los ciclos de release 4+ servicios del mismo equipo
C. Login central No 1 El token viaja en la redirección Cuando el login repetido duela
D. Gateway No, ni dependencia 0 Cabecera falsificable si la red no está cerrada Producción seria, muchos servicios
E. Cliente No 1 El token en el navegador Si ya hay SPA o app móvil

Qué haría yo aquí

Con task-service y tags-service, seguiría con la opción A, pero con una disciplina mínima que la hace tolerable:

  1. La dependencia se mantiene sin cambios: es la frontera de seguridad y debe ser idéntica en todas partes. Si algún día hay que cambiarla, se cambia en todos a la vez, y los tests de los tres servicios la cubren.
  2. El contrato de errores (401 / 503 / 502 con sus mensajes) también se mantiene idéntico, por el mismo motivo.
  3. El cliente del IdP es candidato natural a moverse al user-service (opción C) en cuanto exista una tercera aplicación. No antes: con dos, la duplicación es más barata que el acoplamiento.

El momento exacto del cambio no lo marca el número de servicios, sino una pregunta concreta: "¿cuántas veces al mes me va a doler corregir el login en todos lados a la vez?" Si la respuesta es "una", quédate en A. Si es "varias", ve a C.

El anti-patrón a evitar

Existe una sexta opción que parece sensata y no lo es: convertir el user-service en el dueño de las sesiones de los demás servicios, de forma que task-service y tags-service consulten "quién es el usuario de esta sesión" directamente, sin tokens.

Rota el aislamiento por dentro: el user-service acaba guardando estado de sesión de otras aplicaciones, y cualquier servicio que quiera saber quién es necesita hablar con él de todos modos. Se parece a la opción C pero pierde el control de la sesión, que es justo lo que hace útil al token.

14. Un paquete con código reutilizable

La intuición es correcta y es la respuesta que más se repite en equipos que llevan tiempo con microservicios. Pero conviene separar tres cosas que aquí van mezcladas: qué conviene compartir, con qué mecanismo, y cuándo conviene hacerlo.

Esto ya está en el artículo: lo que se propone es la opción B de la sección 13, un paquete local de uv, con el riesgo de acoplar ciclos de release que allí se menciona. Lo que sigue es el detalle fino: qué se comparte, cómo se hereda y cuándo compensa.

14.1 "Una carpeta" tiene tres problemas que no son de estilo

Antes de elegir la herramienta, hay que ver por qué el naive no funciona. Una carpeta compartida entre servicios parece inocente, pero:

  • Git no comparte historia. Si shared/get_current_user.py vive en el repo de task-service y tags-service la importa, Git no sabe que son el mismo archivo. Un git blame no lleva de un servicio al otro, y el historial de un cambio de seguridad no aparece en ninguno de los dos.
  • Un cambio obliga a mover todos. Si es código compartido, entonces está acoplado: tocarlo significa que todos los servicios consumidores cambian de comportamiento en el mismo momento. Eso no es una carpeta, es un despliegue coordinado disfrazado.
  • Nadie sabe qué es "compartido". En la práctica la carpeta crece hasta que contiene la mitad de la aplicación y nadie sabe qué es API pública y qué es interno de un servicio.

Ese último punto es el que mata las carpetas compartidas en la práctica. La frontera se diluye sola.

14.2 "Heredar" es el mecanismo equivocado

La pregunta sería si los servicios futuros podrían heredar de los módulos del task-service. Conviene separar dos cosas:

HerenciaComposición
tags-service hereda de la dependencia de tasks Cambias la frontera para los dos a la vez Nadie lo nota
tags-service usa la dependencia de tasks Cambias solo un servicio, a propósito El diff lo muestra explícitamente
Cambiar la autenticación a JWT en el futuro Imposible solo en uno Cambias uno, pruebas, decides

El caso del JWT lo deja claro: la sección 12 de este artículo dice que el día que se pase a JWT habrá que cambiar la autenticación. Con herencia no se puede cambiar en un solo servicio sin arrastrar a todos. Con composición, se cambia en uno, se despliega, se mide, y solo después se extiende.

La conclusión no es "nunca heredes", sino: hereda comportamiento, compone decisiones. Una clase base para "toda aplicación web con login" es razonable. Heredar de "la autenticación por HTTP contra el user-service" es casarse con una decisión que explícitamente se dejó abierta para poder cambiarla.

14.3 Lo que de verdad es reutilizable

La pregunta útil no es "¿comparto la dependencia?", sino "¿qué lleva dentro cada módulo: vocabulario o decisiones?"

Candidato¿Qué lleva dentro?Riesgo de compartirloVeredicto
El dict {id, name, email} Solo un contrato de datos Ninguno. Es vocabulario Compartir ya
Chequeo de propiedad (find_owned) Un patrón de autorización por dueño Bajo. Casi todos los servicios lo querrán Compartir ya
Contrato de errores (401 / 503 / 502) La política de cómo se traduce una caída de red Bajo, y evita respuestas inconsistentes Compartir ya
user_service_client URL, timeout, clasificación de errores, y la decisión de validar por HTTP Medio. Es justo lo que se va a cambiar si se pasa a JWT Compartir la interfaz, no la implementación
get_current_user La frontera de seguridad, atada a un proveedor concreto Alto. Es la decisión central del diseño No compartir todavía
Schemas de login (formularios, respuestas) UX: qué se pide y qué se devuelve Bajo técnicamente, alto en fricción de despliegue No compartir (ver 14.2)

La regla que sale de esta tabla: comparte el vocabulario, no las decisiones. "Un usuario autenticado es un dict con id, name y email" es un concepto estable. "Para validar quién es, hay que llamar por HTTP al user-service" es una decisión de arquitectura, y las decisiones se cambian sustituyendo, no heredando.

14.4 Las cinco formas de compartir de verdad

Una vez que se sabe qué se comparte, el mecanismo importa menos de lo que parece:

A. Carpeta copiada a mano

cp ../task-service/app/user_service_client.py app/
cp ../task-service/app/deps.py app/

A favor: cero acoplamiento. Cada servicio se despliega y se rompe solo, y es trivial de entender.
En contra: divergencia silenciosa. Si arreglas un fallo de seguridad, los otros se quedan con la versión vieja, y no hay nada que te avise.

B. Paquete local con path dependency de uv

uv add --path ../packages/microservice-kit

A favor: una fuente de verdad real, y es la opción más simple de montar sin publicar nada.
En contra, y es lo que más muerde: sin versión fijada, un cambio en el paquete aparece en todos los servicios sin que nadie lo decida. Fijar la versión resuelve eso, y en cuanto la fijas estás haciendo releases: el acoplamiento vuelve por la puerta de atrás.

C. Git submodule

A favor: un commit del submodule apunta a un punto exacto del repositorio compartido, así que la trazabilidad es perfecta.
En contra: la experiencia de desarrollo es mala. Todo el mundo odia trabajar con submodules. Clonar, actualizar, resolver conflictos, y un git status que no dice nada útil. Para código de aplicación es una mala señal.

D. Paquete en un registry privado

A favor: la forma profesional. Versionado semántico real, cada servicio fija la versión que le funciona, y se actualiza cuando el equipo lo decide.
En contra: hay que publicar releases de verdad. Un paquete para tres consumidores, donde uno solo es el que produce el cambio, es mucha ceremonia para poca cobertura.

E. Generar en lugar de compartir

En lugar de una dependencia, una plantilla: un comando que al crear un servicio nuevo le estampa el patrón actual. A partir de ahí, cada servicio es libre y diverge sin culpa.

uv run python -m kit.new_service tags
# -> crea tags-service con:
#    - user_service_client.py (copia, editable)
#    - deps.py (copia, editable)
#    - tests que ya pasan contra el user-service real

A favor: combina lo mejor de las dos cosas. Los servicios nuevos nacen consistentes y sus tests ya funcionan, pero después no hay ninguna dependencia que los ate. Un cambio en tags-service no rompe a nadie, y el siguiente servicio lo vuelve a coger con la versión mejorada.
En contra: no resuelve el bug de seguridad en los servicios ya existentes. Para eso hace falta la opción B o D, pero solo para el contrato de datos y el contrato de errores, que es donde no hay decisiones.

14.5 La regla de tres

Existe una regla empírica antigua y sigue siendo la mejor guía: no extraigas hasta la tercera copia.

Con task-service y tags-service hay dos. Extraer con dos instancias es prematuro por dos razones: todavía no sabes qué parte es común y cuál es propia de cada servicio, y el coste del mecanismo no se ha justificado con nadie. Cuando llegue el tercero, ya tendrás la respuesta empírica de qué se parece en la realidad, no en tu imaginación.

14.6 El coste invisible: los tests

Hay un efecto secundario que solo se nota después, y merece su propio párrafo. El código compartido sin tests compartidos es peor que el código duplicado con sus tests:

  • Con código duplicado, cada servicio tiene sus tests y su copia. Si rompes algo, lo detectas en ese servicio. El coste es mantener copias.
  • Con código compartido, los tests viajan con el código, pero solo se ejecutan en el CI de quien tiene el paquete. Si un servicio se actualiza a una versión nueva y el otro se queda atrás, cada uno ejecuta tests distintos sobre el mismo código, y ninguno cubre la combinación.

Por eso, si se comparte algo, lo que se comparte tiene que ser el código junto con sus tests, y el CI de cada servicio tiene que correr la suite de ambos. Si eso no es posible, es una señal de que compartir era la decisión equivocada.

14.7 Mi opinión

Con lo que hay hoy: genera, no compartas. Es decir, la opción E para lo que viene, y no extraer todavía nada.

El orden que propongo, en el tiempo:

  1. Ahora (2 servicios): nada. Duplica si hace falta. Que tags-service tenga su propia copia de la dependencia, y que se llame igual. Las dos van a estar bien durante meses.
  2. Con el tercer servicio: aplica la regla de tres. Mira qué se parece en la realidad y qué no, y entonces decide.
  3. Lo que sí puedes compartir desde ya, y que es gratis: el contrato del dict de identidad y el contrato de errores 401/503/502 (que además evita respuestas inconsistentes entre servicios). Eso entra en una path dependency sin ningún riesgo, porque no contiene ninguna decisión de arquitectura.
  4. Lo que no debes compartir nunca: la decisión de validar por HTTP. Eso vive en cada servicio, y el día que se cambie a JWT o a gateway, se cambia en uno, se despliega, se mide, y solo después se extiende.

Y la regla de oro que resume todo el capítulo: comparte el vocabulario, compone las decisiones.

La trampa de fondo: la sensación de que "compartir código" es sin coste de verdad. Compartir es la manera barata de no volver a escribir, pero paga en no poder cambiar. En un sistema que todavía está cambiando de arquitectura —y este lo está, de HTTP a JWT a gateway— esa es justo la moneda que no quieres gastar.

15. Limitaciones honestas

  • Sin circuit breaker. Con el user-service colgado, cada request espera el timeout completo (2 s) antes de rendirse. Un circuit breaker lo convertiría en un fallo inmediato.
  • Un salto de red en cada request. Aquí son ~2 ms medidos; multiplicado por latencia alta y concurrencia, es el techo de escalado del diseño.
  • Introspección sin caché. Cada request autenticado toca la base de datos del user-service. No hay caché de identidad: con TTL de 60 minutos y revocación inmediata, cachear la identidad sería reabrir la ventana que el token opaco cerró.
  • Sin refresh tokens. El cliente tiene que pedir un token nuevo con la contraseña cuando caduca (60 minutos). Aceptable en local, incómodo en una app real.
  • Sin rate limiting en la emisión. POST /api/tokens es el endpoint que recibe contraseñas: el primero que debería estar limitado. La versión Laravel de esta serie lo añadió como capítulo aparte; aquí tocará lo mismo.
  • Una sola identidad. No hay roles ni permisos. Cualquier usuario autenticado puede tocar sus propias tareas, que es lo correcto, pero no hay un modelo de autorización más rico.
  • Sin interfaz web. El cliente es siempre un programa que manda el header. La sesión web con token guardado es el capítulo que esta versión del proyecto no tiene (ver sección 7).

Nota: la implementación usa tokens opacos generados con secrets.token_hex y almacenados como SHA-256, sin bibliotecas de auth añadidas: PBKDF2 viene de la biblioteca estándar. La validación se hace por HTTP contra el user-service en cada request, de forma deliberada, para poder observar el costo en lugar de teorizarlo.
