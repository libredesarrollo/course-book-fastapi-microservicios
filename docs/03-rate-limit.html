Rate limiting en el login: el antes y el después

Resumen: el user-service exponía POST /api/tokens sin ninguna protección. Medido: ~3 700 intentos de contraseña por minuto, las 24 horas del día. Este capítulo recoge qué había antes, qué se añadió después, por qué son dos límites y no uno, y los tres errores que aparecieron al implementarlo.

Contexto: es el endpoint que recibe contraseñas. No es un endpoint cualquiera — es la puerta de entrada al sistema de identidad, y por lo tanto el objetivo natural de cualquier intento de fuerza bruta.

1. El estado anterior

La ruta era exactamente esto:

@router.post("/tokens", response_model=TokenIssued, status_code=201)
def issue_token(payload: TokenRequest, db: Session = Depends(get_db)) -> TokenIssued:
    user = db.query(User).filter(User.email == payload.email).first()

    if user is None or not security.verify_password(payload.password, user.password):
        raise HTTPException(status_code=401, detail="Credenciales inválidas")
    ...

Sin dependencias de seguridad. El handler hacía su trabajo y ya. A favor de esta versión, una cosa sí la tenía bien desde el capítulo 1: el token se emitía con caducidad obligatoria (expires_at NOT NULL, TTL de 60 minutos). Lo que faltaba era el resto.

Las dos carencias

Estado anteriorRiesgo
Sin rate limit El endpoint aceptaba intentos ilimitados Fuerza bruta contra contraseñas. La más grave de las dos.
Sin registro Un 401 no dejaba rastro Una fuerza bruta era completamente silenciosa. Nadie se enteraba hasta que un usuario perdía su cuenta.

El detalle que lo hace más grave: aquí no existe la excusa del "pero la web tenía su propio throttle", que fue lo que encontró la versión Laravel de esta misma serie (una UI con throttle:6,1 junto a una API desnuda). En este proyecto el capítulo 1 es API puro, así que no había ni la ilusión de protección: el endpoint abierto era el único camino.

2. La medición que lo destapó

Cincuenta intentos con contraseña incorrecta, medidos contra el servidor de verdad:

$ for i in $(seq 1 50); do
    curl -s -o /dev/null -X POST http://127.0.0.1:8000/api/tokens \
      -H "Content-Type: application/json" \
      -d '{"email":"ana.torres@example.com","password":"intento'$i'"}'
  done

  50 intentos en 0.81 s -> ~3 700 req/min sin ninguna protección

Un atacante con una conexión decente multiplica esa cifra por cien sin esfuerzo. Y como la base de usuarios es SQLite con dos filas, el cuello de botella lo pone el proceso, no el almacenamiento: a escala real el número sería mayor. (La versión Laravel de este mismo experimento midió 8 439 req/min; el número no importa, la orden de magnitud sí.)

La lección del método: no hubo que leer el código para saber que faltaba algo. Bastó con pedir lo que un atacante pediría y medirlo. Un rate limit que no has probado no existe.

4. La configuración

Todo sale de app/config.py:

# Límites de intentos de login sobre POST /api/tokens (recibe contraseñas).
# Dos contadores: por cuenta (martilleo) y por IP (barrido de emails).
LOGIN_THROTTLE_PER_ACCOUNT = _int("LOGIN_THROTTLE_PER_ACCOUNT", 5)
LOGIN_THROTTLE_PER_IP = _int("LOGIN_THROTTLE_PER_IP", 20)
LOGIN_THROTTLE_DECAY_SECONDS = _int("LOGIN_THROTTLE_DECAY_SECONDS", 60)

Y en el entorno, si hace falta apretarlos o aflojarlos:

LOGIN_THROTTLE_PER_ACCOUNT=5
LOGIN_THROTTLE_PER_IP=20
LOGIN_THROTTLE_DECAY_SECONDS=60

Por qué variables de entorno y no constantes en el código: cambiar un límite de 5 a 20 no debería requerir un deploy. Es una decisión operativa, y las decisiones operativas viven en el entorno.

5. Por qué dos límites y no uno

El limitador vive en app/rate_limit.py y es una función con dos contadores:

def check_login(request: Request, email: str) -> None:
    """Dos contadores porque son dos ataques distintos:
    - por IP: un barrido de muchas cuentas desde un mismo origen;
    - por cuenta (clave email+IP): una sola cuenta martilleada desde una IP.
    Cuenta TODO intento, no solo los fallidos: un límite que solo frena los
    errores es decorativo, basta acertar en el intento 21."""
    now = time.monotonic()
    ip = client_ip(request)
    pairs = (
        (f"ip:{ip}", config.LOGIN_THROTTLE_PER_IP),
        (f"email:{_email_key(email)}|ip:{ip}", config.LOGIN_THROTTLE_PER_ACCOUNT),
    )
    with _lock:
        for key, limit in pairs:
            hits = _hits[key]
            while hits and now - hits[0] >= config.LOGIN_THROTTLE_DECAY_SECONDS:
                hits.popleft()
            if len(hits) >= limit:
                wait = int(config.LOGIN_THROTTLE_DECAY_SECONDS - (now - hits[0])) + 1
                raise HTTPException(
                    status_code=429,
                    detail="Demasiados intentos de login; inténtalo más tarde",
                    headers={"Retry-After": str(wait)},
                )
        for key, _limit in pairs:
            _hits[key].append(now)

Son dos ataques distintos y cada uno necesita su contador:

Ataque¿Lo frenaría un solo límite de 20/min?Qué lo detiene aquí
Una cuenta, una IP
La forma más común		 Sí, pero tardaría 20 intentos El de cuenta corta en 5
Una cuenta, muchas IP
Botnet o proxys rotos		 No. Cada IP tiene su presupuesto y ninguno se agota El de cuenta lleva la IP en la clave, así que cambia al cambiar la IP… pero combinado con el de IP, el atacante tampoco puede rotar libremente
Muchas cuentas, una IP
Barrido de emails		 Sí, a los 20 intentos El de IP corta en 20

Se aplica el más estricto de los dos. En cuanto uno se agota la respuesta es 429, y los intentos posteriores también cuentan como consumido, así que agotar uno agota ambos.

Detalle de la clave por cuenta: lleva la IP. Si no, el límite por cuenta se compartiría entre todas las IP, y el atacante solo tendría que rotar IP para no agotarlo nunca.

Y un detalle de implementación: la ventana es deslizante — cada intento vale 60 segundos desde que ocurrió. La contabilidad cabe en una cola por clave, y el reset() existe para que los tests no se hereden contadores entre sí.

6. Dónde se aplica

def rate_limit_login(request: Request, payload: TokenRequest) -> None:
    """Fuerza bruta contra el endpoint que recibe contraseñas: dos contadores
    con los límites y la ventana de app/config.py."""
    check_login(request, payload.email)


@router.post(
    "/tokens",
    response_model=TokenIssued,
    status_code=201,
    dependencies=[Depends(rate_limit_login)],
)

En FastAPI, una dependencia declarada en dependencies=[...] corre antes del handler y puede pedir el body (TokenRequest) — FastAPI lo parsea una sola vez y lo reutiliza, así que el email está disponible sin doble validación.

El límite va en la ruta, no en el handler ni como middleware global. Solo este endpoint recibe contraseñas. Un límite global frenaría también GET /api/user, que es justo lo que un cliente activo hace sin parar en cada request.

7. Caducidad: por qué NOT NULL

Esta mitad del capítulo Laravel ya venía hecha: desde el capítulo 1, expires_at es NOT NULL y la emisión no admite token sin TTL. Conviene dejar aquí el porqué, porque es la misma clase de decisión:

# Opción A — la habitual: opcional, y confiar en que se rellene
expires_at: Mapped[datetime | None]

# Opción B — la elegida: imposible olvidar la caducidad
expires_at: Mapped[datetime]            # NOT NULL, sin valor por defecto
security.expiry()                       # obligatorio en la emisión

Un token sin caducidad es un token robado que sirve para siempre. Con la opción A bastaba crear una fila sin expires_at y nacía un token eterno, sin que nada fallara ni avisara. Con la B el error no se puede cometer, y la consulta de validación no necesita el whereNull(...)->orWhere(...) que en la opción A es exactamente el tipo de condición que se olvida revisar en una refactorización — su error sería aceptar tokens que deberían haber caducado.

8. Qué se registra y qué no

Cada intento fallido deja un warning:

# stderr del user-service
WARNING:user-service:Failed login attempt {"email": "ana.torres@example.com", "ip": "127.0.0.1", "account_exists": true}
WARNING:user-service:Failed login attempt {"email": "nadie@example.com", "ip": "127.0.0.1", "account_exists": false}

Y también las operaciones que cambian el estado de un token:

INFO:user-service:API token issued {"user_id": 1, "device": "api-token", "expires_at": "2026-11-11T11:34:07.729129+00:00"}
INFO:user-service:API token revoked {"user_id": 1, "device": "api-token"}

Por qué registrar account_exists

La respuesta al cliente es idéntica en ambos casos ("Credenciales inválidas", 401), y tiene que serlo: si no, el endpoint sirve para enumerar qué emails están dados de alta.

Pero en el log la información sí es útil: un pico de intentos con account_exists: true contra muchos emails distintos es la firma de credential stuffing, y es justo lo que se quiere poder detectar.

Por qué no se registra la contraseña

Nunca. Y no es una convención: hay un test que lo comprueba.

def test_nunca_registra_la_contrasena(caplog):
    seed_two_users()
    with caplog.at_level(logging.WARNING, logger="user-service"):
        with client() as c:
            _login(c, password="mi-secreto-muy-largo")
    assert "mi-secreto-muy-largo" not in caplog.text

El riesgo de escribir contraseñas en el log es subestimado. Los logs suelen tener permisos más laxos que la base de datos, se copian a agregadores de terceros, y se conservan meses. Un log de autenticaciones es material de credential stuffing listo para usar.

9. Verificación real

Fuerza bruta contra una cuenta

$ for i in $(seq 1 9); do curl -X POST .../api/tokens -d '{...}'
  intento 1 -> 401
  intento 2 -> 401
  intento 3 -> 401
  intento 4 -> 401
  intento 5 -> 401
  intento 6 (CONTRASEÑA CORRECTA) -> 429 + Retry-After: 60
  intento 7 -> 429
  intento 8 -> 429
  intento 9 -> 429
[■][■][■][■][■][ ][ ][ ][ ]
 401 401 401 401 401 429 429 429 429

■ = intento aceptado por el limitador (credencial incorrecta, 401)
  = bloqueado (429 Too Many Requests)

El intento 6 llevaba la contraseña correcta, y el límite lo bloqueó igual: los contadores cuentan todos los intentos. Un límite que solo frena los fallos es decorativo.

Barrido contra 24 cuentas distintas desde una IP

401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401 401
429 429 429 429

Cada intento usa una cuenta diferente, así que el límite por cuenta nunca se agota. El de IP es el que corta, exactamente al llegar a 20. En el log quedaron los 20 con account_exists: false.

Cuánto protege en números

$ 50 intentos medidos antes del cambio: 50 intentos en 0.81 s -> ~3 700 req/min
$ 50 intentos medidos después:          50 intentos en 0.43 s
  de los cuales SOLO 20 tocaron contraseñas; los 30 restantes fueron 429 instantáneos

El atacante sigue teniendo velocidad de máquina, pero su presupuesto de contraseñas por minuto baja de 3 700 a 20 (por IP) o 5 (por cuenta). Eso es lo que hace descartable la fuerza bruta contra una contraseña elegida por humanos.

Efecto en el otro servicio

El task-service no necesitó cambios: su frontera ya traducía el 401 a "Token inválido o expirado". Comprobado en vivo:

login correcto -> 201
GET /api/tasks con el token (via task-service) -> 200
POST /api/tokens con el presupuesto IP agotado -> 429   # el login, no el uso del token

Y ese último punto marca la frontera del cambio: el límite protege la emisión de tokens, no el uso. Con un token válido en mano, seguir usándolo no cuenta en ningún contador — el límite del login solo existe porque el login es lo único que expone contraseñas.

10. Tres errores al implementarlo

Los tres aparecieron en la suite mientras se implementaba, no después.

10.1 El test que contó el token de otro test

"Un intento fallido no emite ningún token" contaba ApiToken.count() y dio más de cero. El intento fallido no emitía nada — el token era de un test anterior, que había hecho un login correcto y dejado su fila en la base de datos compartida (:memory: con StaticPool persiste entre tests).

La solución: el seed de los tests borra también las filas de api_tokens, igual que borra los usuarios. Es el mismo principio de la fixture autouse que limpia los overrides de identidad y los contadores del limitador: nadie arrasta estado del test anterior.

10.2 La aserción que peleaba con el formato del JSON

El test del log pedía exactamente "account_exists":true y el json.dumps produce "account_exists": true (con espacio). La información era correcta; la aserción peleaba con el separador por defecto en vez de comprobar lo que importa: que el email está, que la IP está, que la existencia de la cuenta está.

La lección: una aserción sobre formato exacto es frágil por definición. Comprueba los campos que importan, no el espaciado de la serialización.

10.3 Los logs que "ya estaban" y nadie veía

El log.info("API token issued", ...) existía y el grep del E2E no lo encontraba. Causa: sin un handler configurado, Python descarta todo lo que es INFO (el último recurso de logging solo emite WARNING en adelante). El registro estaba escrito, pero en producción virtual iba a ninguna parte.

La solución: logging.basicConfig(level=logging.INFO) en main.py, con un comentario de por qué existe. Es la versión Python del "wrote the log but forgot the sink" — el mensaje existe, el destinatario no.

11. La trampa de los proxies

El límite por IP usa la IP del socket (request.client.host), no de las cabeceras. Es la decisión correcta por defecto — X-Forwarded-For se escribe a mano con un curl — pero tiene la trampa de siempre en el otro extremo:

$ curl -H "X-Forwarded-For: 203.0.113.9" -X POST .../api/tokens ...
  401     # la cabecera se ignoró: contó como 127.0.0.1 otra vez (correcto)

La consecuencia en producción es seria y silenciosa: si el servicio corre detrás de un balanceador o un ingress, todas las peticiones llegan con la IP del proxy, y el límite por IP se convierte en un límite global compartido. Con veinte intentos de login en todo el sistema, se bloquea a todo el mundo.

# uvicorn sabe leer el header real, pero SOLO de IPs proxy declaradas:
$ uvicorn app.main:app --port 8000 --proxy-headers \
    --forwarded-allow-ips "10.0.0.5"   # la IP de tu proxy, no "*"

No se activó en este proyecto a propósito: no hay proxy en local, y activarlo con * reabriría exactamente la puerta que cerramos (cualquiera puede falsificar X-Forwarded-For si el servidor confía en cualquiera). Es el primer paso antes de desplegar, y conviene dejarlo anotado junto al límite, no descubrirlo en producción.

13. Lo que queda abierto

  • Contadores en memoria del proceso. La cola de hits vive en el proceso de uvicorn. Con una sola instancia, es lo correcto; con N réplicas, el atacante dispone de N presupuestos. En producción, contadores compartidos (Redis) o un proxy delante que ya limite. Es la más importante de la lista: un rate limit en memoria local solo protege cuando hay una sola instancia.
  • Sin límite global de peticiones. Ahora solo se protege el login. Un atacante podría martillear GET /api/user sin consecuencias.
  • Sin bloqueo de cuenta. El rate limit frena el ritmo, pero no invalida la cuenta. En muchos sistemas eso es justo lo que se quiere: un atacante lento no se ve afectado y el usuario legítimo tampoco.
  • Sin aviso al usuario legítimo. La respuesta 429 dice "demasiados intentos" y cuánto falta (Retry-After), pero una UI real explicaría qué pasó y qué hacer.
  • Sin refresh tokens. Cuando el token caduca (60 min), el usuario vuelve a escribir su contraseña — y con el presupuesto por cuenta, una mala suerte repetida puede toparse con el límite. El sitio está previsto: POST /api/tokens/refresh, cambiar el token caducado por uno nuevo.

La de contadores por proceso es la más importante. Es el error que hace que un sistema desplegado con varias réplicas crea estar protegido y no lo esté: cada réplica le regala al atacante un presupuesto entero de contraseñas.

Nota: los contadores viven en app/rate_limit.py, la configuración en app/config.py (env LOGIN_THROTTLE_*), el límite se aplica como dependencia en la ruta POST /api/tokens, y el registro de intentos en routes_tokens.issue_token(). Todo está en el user-service porque es el único que recibe contraseñas: el task-service no tiene ni usuario ni contraseña que proteger.
