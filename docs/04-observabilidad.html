Observabilidad entre microservicios: correlation ID, health checks y trazabilidad

Resumen: al pasar de dos aplicaciones aisladas a dos microservicios que se llaman por HTTP, la pregunta deja de ser "¿ha funcionado?" para pasar a ser "¿qué petición ha provocado este error?". Para responderla hay que poder seguir un único identificador a lo largo de toda la cadena. Este capítulo recoge lo que acabamos de implementar en la versión FastAPI: X-Request-Id, health checks, propagación entre servicios y logs correlacionados.

Contexto: proyecto demo-microservicios con user-service (FastAPI, puerto 8000) y task-service (FastAPI, puerto 8001), comunicación HTTP síncrona y autenticación delegada.

1. El problema: peticiones sin rastro

En una app monolítica basta con abrir la salida de uvicorn y filtrar por ruta. En microservicios la realidad es otra:

  • Una acción del cliente contra el task-service provoca una llamada interna a GET /api/user del user-service en cada petición autenticada.
  • Si falla la red, el 503 aparece solo en los logs del task-service, pero ¿qué cliente lo provocó? no se sabe.
  • Si hay varios usuarios en paralelo, las líneas se entremezclan y resulta imposible reconstruir el camino completo.

Sin un identificador común, depurar entre dos servicios es adivinar.

2. Objetivo del capítulo

El objetivo no es instrumentación completa con OpenTelemetry. Es algo mucho más práctico:

  1. Poder trazar una petición desde que llega al task-service hasta la llamada que hace al user-service, con el mismo ID.
  2. Saber si los servicios están vivos sin necesidad de autenticar.
  3. Propagar la traza entre ambos servicios por HTTP.
  4. Correlacionar los logs para poder filtrar por request_id y seguir el recorrido completo.

3. Correlation ID: X-Request-Id

La convención es la misma de la serie: usar la cabecera HTTP X-Request-Id.

  • Si llega del cliente (o del servicio que nos llama): se respeta. No se genera uno nuevo.
  • Si no llega: se genera un UUID v4 con uuid.uuid4().
  • Siempre se devuelve en la respuesta con la misma cabecera X-Request-Id.

Así, cualquier herramienta, proxy o el propio desarrollador puede pasar ese ID y el sistema lo mantendrá durante toda la cadena.

4. El middleware en app/observability.py

Toda la pieza vive en un solo módulo por servicio: app/observability.py. Los dos servicios son proyectos uv independientes y no comparten código (no hay equivalente al paquete de Composer de la serie Laravel), así que el módulo va duplicado en cada servicio — igual que ya lo están db.py y config.py.

class RequestIdMiddleware(BaseHTTPMiddleware):
    async def dispatch(
        self, request: Request, call_next: Callable[[Request], Awaitable[Response]]
    ) -> Response:
        rid = request.headers.get(REQUEST_ID_HEADER) or str(uuid.uuid4())
        token = request_id.set(rid)
        try:
            response = await call_next(request)
        finally:
            request_id.reset(token)
        response.headers[REQUEST_ID_HEADER] = rid
        return response

Tres decisiones que valen la pena nombrar:

  • El ID vive en un ContextVar, no en la request: cualquier código de la petición lo lee sin tener que arrastrar el objeto Request — y las llamadas salientes (que no reciben la request) lo ven igual.
  • El reset() va en el finally: si la petición revienta, el contexto no se queda contaminado para la siguiente.
  • Se fija antes de call_next porque es lo que hace que el ContextVar alcance hasta los endpoints síncronos (el threadpool de Starlette hereda el contexto tal como está en ese momento).

Se monta con app.add_middleware(RequestIdMiddleware) en el main.py de cada servicio.

5. Logs con contexto: ContextVar + Filter

Sin contexto, los logs eran así:

WARNING:user-service:Failed login attempt {"email":"ana.torres@example.com","ip":"127.0.0.1","account_exists":true}

El request_id no aparece, así que no se puede cruzar con la respuesta HTTP ni con los logs del otro servicio. El equivalente en Python del Log::withContext() de Laravel es un filtro de logging que lee el ContextVar:

class RequestIdFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id.get() or "-"
        return True


class RequestIdFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        if not hasattr(record, "request_id"):
            record.request_id = "-"
        return super().format(record)


def configure_logging(*loggers: str) -> None:
    logging.basicConfig(level=logging.INFO)
    formatter = RequestIdFormatter(
        "%(levelname)s:%(name)s:%(message)s request_id=%(request_id)s"
    )
    for handler in logging.getLogger().handlers:
        handler.setFormatter(formatter)
    for name in loggers:
        logging.getLogger(name).addFilter(RequestIdFilter())

Dos detalles de diseño:

  • El filtro va en el logger, no en el handler. Los filtros de un handler no alcanzan a los records que captura caplog en los tests; los del logger sí se aplican a cada record antes de que salga a cualquier handler.
  • El formatter completa con "-" los records que no nacieron dentro de una petición (arranque, seed, logs de librerías). Sin ese default, cualquier log de httpx2 rompería el formato con un KeyError.

Y en el main.py de cada servicio, una sola línea sustituye al basicConfig suelto:

configure_logging("user-service")   # en el task-service: configure_logging("task-service")

Los mensajes de negocio no cambiaron: siguen llevando sus campos como JSON en el propio mensaje. El request_id se añade solo, al final de cada línea.

6. Health checks

Se ha añadido un GET /health público en los dos servicios, sin autenticación:

@app.get("/health")
def health() -> dict[str, str]:
    return {
        "status": "ok",
        "service": "user-service",
        "timestamp": datetime.now(UTC).isoformat(),
    }

El payload es estático a propósito. Un health check no debe depender de la base de datos, porque el caso interesante es justo el de la base de datos caída: si consultara la base de datos para saber si está bien, no podría distinguir "estoy vivo pero sin base de datos" de "estoy muerto", y el balanceador necesita esa diferencia.

7. Propagación al user-service desde task-service

El task-service llama al user-service en cada petición autenticada: verify_token() → GET /api/user. Toda la frontera vive en un solo archivo, task-service/app/user_service_client.py, así que la propagación va ahí:

def _trace_headers() -> dict[str, str]:
    """Propaga el correlation ID que llegó del cliente, para que la misma
    petición pueda seguirse en los logs de los dos servicios."""
    rid = request_id.get()
    return {REQUEST_ID_HEADER: rid} if rid else {}


def verify_token(token: str) -> dict[str, Any]:
    try:
        resp = _http_get(
            f"{config.USER_SERVICE_URL}/api/user",
            headers={"Authorization": f"Bearer {token}", **_trace_headers()},
        )
    ...

De paso, la frontera dejó de fallar en silencio. Los tres caminos de error ahora dejan warning antes de responder:

  • ConnectError/ConnectTimeout → user-service unreachable {"base_url": ..., "path": "/api/user"} antes del 503.
  • 401 del IdP → Token rejected by user-service antes del 401 local.
  • Status inesperado → Unexpected response from user-service {"status": ...} antes del 502.

Nunca se loguea el token en sí: solo que fue presentado y rechazado. El request_id va aparte, metido por el filtro.

8. Comprobación en vivo

Con ambos servidores arrancados en local:

$ curl -si http://127.0.0.1:8000/health | grep -i x-request-id
x-request-id: a4a11e95-9f7c-4c33-a58f-8dcdbdf21c7b

$ curl -si -H "X-Request-Id: prueba-trazabilidad-123" http://127.0.0.1:8001/health | grep -i x-request-id
x-request-id: prueba-trazabilidad-123

Si se pasa un ID explícito, se mantiene. Al pedir una tarea con un token podrido, ese mismo ID viaja al user-service en la llamada de verify_token — y aparece dentro del log del servicio que rechazó:

$ curl -s -H "X-Request-Id: traza-e2e-001" -H "Authorization: Bearer token-podrido" http://127.0.0.1:8001/api/tasks

WARNING:task-service:Token rejected by user-service request_id=traza-e2e-001

Y el caso que abre el capítulo — el IdP caído — deja la respuesta a "¿qué cliente lo provocó?":

WARNING:task-service:user-service unreachable {"base_url": "http://127.0.0.1:8000", "path": "/api/user"} request_id=...

El otro lado cuenta su parte con el mismo ID:

$ curl -s -X POST -H "X-Request-Id: traza-e2e-001" -H "Content-Type: application/json" \
    -d '{"email":"ana.torres@example.com","password":"mala"}' http://127.0.0.1:8000/api/tokens

WARNING:user-service:Failed login attempt {"email": "ana.torres@example.com", "ip": "127.0.0.1", "account_exists": true} request_id=traza-e2e-001

Con ese request_id se puede filtrar en la salida de los dos servicios y reconstruir la petición completa:

$ grep "traza-e2e-001" /tmp/uvicorn-8000.log /tmp/uvicorn-8001.log

9. Tests

Un archivo nuevo por servicio, tests/test_observability.py, fija el contrato completo:

  • user-service (4 tests): health sin autenticar ni tocar la BD, ID generado es UUID v4, el ID del cliente se respeta, y el request_id llega al record de Failed login attempt.
  • task-service (5 tests): health sin autenticar, el ID del cliente se respeta, el ID del cliente y el generado se propagan en la llamada saliente (capturando las cabeceras que recibe _http_get), y el request_id llega al warning user-service unreachable cuando el IdP está caído.

El test del filtro merece una mención: caplog captura los records en un handler propio, así que un filtro colgado del handler no lo vería. Por eso el RequestIdFilter va en el logger — y por eso el test puede asertar directamente record.request_id == "traza-e2e-002".

10. ¿Por qué antes de reintentos?

En user_service_client.py está previsto añadir reintentos ante errores de red. Eso está bien, pero tiene un problema sin trazabilidad:

  • Sin contexto: ConnectError → ¿es el primer intento o el tercero? Difícil de distinguir.
  • Con request_id en los logs: verás las N líneas con el mismo request_id y sabrás que son reintentos de la misma petición.
  • Con propagación cruzada: también podrás buscar ese request_id en el log del user-service y ver si llegó alguna vez o si nunca salió del task-service.

Por eso se ha optado por logs con contexto antes que reintentos. Es el orden correcto para poder depurar lo que venga después.

12. Estado actual

Tras implementar lo anterior:

  • Tests: user-service 21 tests — OK. task-service 16 tests — OK.
  • Operabilidad: ya se puede obtener X-Request-Id en todas las respuestas, propagado entre servicios.
  • Trazabilidad: el mismo ID aparece en los logs de los dos servicios; los tres errores de la frontera dejan warning propio en el task-service.
  • Health: GET /health público en los dos puertos, payload estático, sin BD ni autenticación.
