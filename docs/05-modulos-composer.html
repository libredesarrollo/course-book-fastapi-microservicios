Empaquetar el código común: una librería interna empaquetada con uv

Resumen: cuando dos microservicios comparten código, hay tres caminos: copiar y pegar, publicar en PyPI, o un paquete local instalado por ruta. Este capítulo explica el tercero: cómo se extrae el código duplicado a packages/, cómo se declara el pyproject.toml del paquete, cómo lo consumen las aplicaciones con uv add --editable, y por qué el resultado equivale al symlink de los repositorios path de Composer.

Aplicado en el proyecto demo-microservicios, que tiene user-service y task-service con el módulo de observabilidad duplicado byte a byte.

1. El problema: código duplicado

El capítulo de observabilidad terminó con el mismo módulo viviendo en dos sitios:

user-service/app/observability.py    (~115 líneas)
task-service/app/observability.py    (~115 líneas)   <- idéntico, byte a byte

Y el endpoint de health también: el GET /health de los dos servicios difiere en un solo campo, el nombre.

El problema real no es el tamaño:

El problema real es la divergencia. Si mañana hay que cambiar el formato del request_id, hay que recordar cambiarlo en dos sitios. Si se cambia en uno y no en el otro, el task-service genera IDs con un formato y el user-service con otro. Y el síntoma aparece en producción, un martes, sin ningún test que lo detecte.

Ese es el momento en que el código duplicado deja de ser "un poco feo" y pasa a ser un riesgo operativo.

2. Las tres opciones y por qué esta

OpciónVentajasInconvenientes
A. Copiar y pegar Cero infraestructura, funciona siempre Divergencia silenciosa. Es lo que acabamos de tener.
B. Publicar en PyPI Instalable desde cualquier sitio, versionado de verdad Requiere cuenta, tokens, CI para publicar. Innecesario para un monorepo de 2 servicios.
C. Paquete local por ruta, editable Versionable con Git, sin publicar nada, los cambios se ven al instante Hay que declararlo en el pyproject.toml de cada consumidor

Elegimos la C. En un monorepo es la opción estándar: se obtiene el beneficio de la modularidad (una sola copia del código, un solo sitio que cambiar) sin el coste de publicar nada.

El equivalente exacto de los repositorios path de Composer en el mundo Python/uv es una dependencia editable por ruta: [tool.uv.sources] con editable = true. No es un workspace de uv: cada servicio sigue siendo un proyecto uv independiente con su propio uv.lock; solo comparten el paquete, como los servicios Laravel compartían el paquete por vendor/.

3. Estructura resultante

demo-microservicios/
├── packages/
│   └── microservices-observability/
│       ├── pyproject.toml          <- el "composer.json" del paquete
│       ├── README.md
│       └── src/
│           └── demo/
│               └── microservices/
│                   └── observability/
│                       └── __init__.py     <- TODO el código, en un solo sitio
│
├── user-service/
│   ├── pyproject.toml              <- + [tool.uv.sources], + dependency
│   └── app/
│       ├── main.py                 <- 3 líneas: configure_logging, add_middleware, add_health
│       └── (observability.py borrado)
│
└── task-service/
    ├── pyproject.toml              <- + [tool.uv.sources], + dependency
    └── app/
        ├── main.py                 <- igual, con su nombre de servicio
        ├── user_service_client.py  <- se queda: consume el ContextVar del paquete
        └── (observability.py borrado)

El principio de la estructura: en packages/ va lo que es compartido; en app/ va lo que es de cada servicio. Un paquete que solo usa un servicio no es un paquete: es código que se mudó de sitio sin ganancia.

4. El pyproject.toml del paquete

Este es el de packages/microservices-observability, entero:

[project]
name = "microservices-observability"
version = "0.1.0"
description = "Correlation ID, health check y logs con contexto para microservicios FastAPI (capítulo 5)"
requires-python = ">=3.13"
dependencies = [
    "starlette>=0.40",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/demo"]

Qué significa cada clave

ClaveValorPor qué
dependencies Solo starlette El paquete usa BaseHTTPMiddleware, Request, JSONResponse y el router de Starlette. No declara fastapi: no obliga a instalar el framework completo. Es el equivalente directo de declarar illuminate/* y no laravel/framework en el paquete Composer de la serie.
build-system hatchling Quién convierte src/ en un paquete instalable. Es el rol de composer install generando el autoloader.
tool.hatch.build.targets.wheel.packages ["src/demo"] El raíz del namespace: le dice a hatchling que empaquete demo/ entero tal cual, sin crear paquetes fantasma.
requires-python >=3.13 El mismo piso que los servicios de la serie.

Qué contiene el paquete

  • RequestIdMiddleware: respeta el X-Request-Id entrante o genera un UUID v4; siempre lo devuelve en la respuesta.
  • request_id: el ContextVar compartido que el middleware fija y que cualquier código de la petición lee (incluidas las llamadas salientes del task-service).
  • RequestIdFilter / RequestIdFormatter / configure_logging: el request_id en cada línea de log sin pasarlo a mano.
  • add_health(app, service): publica el GET /health con payload estático.
  • REQUEST_ID_HEADER: la constante de la convención, en un solo sitio.

5. El namespace: PEP 420 es el PSR-4 de Python

En la serie Laravel, el paquete vive bajo Demo\Microservices\Observability\ porque el prefijo de namespace es el que declara de quién es el código. El equivalente en Python es el namespace package de PEP 420: los directorios demo/ y demo/microservices/ no llevan __init__.py; solo la hoja lo lleva:

src/
└── demo/                       <- namespace: SIN __init__.py
    └── microservices/          <- namespace: SIN __init__.py
        └── observability/
            └── __init__.py     <- la hoja: CON __init__.py

La gracia de PEP 420: cuando llegue el segundo paquete (demo/microservices/user_service_client), los dos coexistirán bajo el mismo namespace demo.microservices sin conflicto — el import ya no dice dónde vive el código, dice de quién es.

Detalle importante: si se pusiera un __init__.py en demo/, el primer paquete en resolverse "capturaría" el namespace y el segundo paquete volaría en tiempo de import. La regla es estricta: los niveles del namespace van siempre sin __init__.py.

6. El pyproject.toml de la aplicación

En user-service/pyproject.toml y task-service/pyproject.toml se han añadido dos cosas.

6.1 El bloque sources

[tool.uv.sources]
microservices-observability = { path = "../packages/microservices-observability", editable = true }

El path es relativo al directorio del servicio. Por eso es ../packages/... y no una ruta absoluta: el proyecto se puede clonar en cualquier sitio y sigue funcionando.

6.2 El bloque dependencies

dependencies = [
    "fastapi>=0.115",
    ...
    "microservices-observability",
]

Se registró con el comando real:

$ cd user-service && uv add --editable ../packages/microservices-observability
   Building microservices-observability @ file:///…/packages/microservices-observability
      Built microservices-observability @ file:///…/packages/microservices-observability
 + microservices-observability==0.1.0 (from file:///…/packages/microservices-observability)

6.3 Las dos mitades juntas

Una de las dos piezas no basta:

  • El [tool.uv.sources] le dice a uv dónde está el paquete y que lo enlace en modo editable.
  • El dependencies le dice que lo quieres.

Con las dos, uv lo resuelve (y lo deja apuntado en uv.lock). Con solo una, o no lo encuentra o no lo instala.

7. Por qué editable y no una copia

Esta es la parte que conviene entender, porque cambia cómo se trabaja. Después del uv add, el paquete no está copiado en el venv: apunta al árbol fuente:

$ cd task-service && uv run python -c "import demo.microservices.observability as m; print(m.__file__)"
/Users/…/demo-microservicios/packages/microservices-observability/src/demo/microservices/observability/__init__.py

El __file__ del módulo vive en packages/, no en .venv/. Es el equivalente al symlink de vendor/demo/microservices-observability de la serie Laravel.

Lo que eso permite

$ vim packages/microservices-observability/src/demo/microservices/observability/__init__.py
# guardar, y listo: los dos servicios ya usan el cambio

Sin ejecutar uv add otra vez. Sin reinstalar nada. Sin riesgo de tener una versión del paquete en el venv y otra en packages/.

Lo que hay que vigilar

RiesgoQué pasaCómo se evita
El enlace editable se pierde al recrear el venv Un uv sync lo recrea solo: la fuente está en uv.lock y el pyproject.toml, que sí se versionan Nada que hacer a mano
Editar el paquete y no ver el cambio Solo puede pasar si se instaló sin editable = true (copia congelada) El bloque sources del consumidor manda; se corrige ahí
Consumidor fuera del repo Un servicio que no viva junto a packages/ no encuentra la ruta relativa En despliegue, se publica el paquete (PyPI privado) o se despliega el monorepo completo

8. add_health: el HealthController del paquete

El GET /health estaba duplicado en los dos main.py, difiriendo solo en el nombre del servicio. Ahora el payload vive en un solo sitio, y cada aplicación decide en qué app lo monta y con qué nombre:

def add_health(app: Starlette, service: str) -> None:
    def health(request: Request) -> JSONResponse:
        return JSONResponse(
            {
                "status": "ok",
                "service": service,
                "timestamp": datetime.now(UTC).isoformat(),
            }
        )

    app.add_route("/health", health, methods=["GET"])

El payload es estático a propósito. Un health check no debe depender de la base de datos, porque el caso interesante es justo el de la base de datos caída: si consultara la base de datos para saber si está bien, no podría distinguir "estoy vivo pero sin base de datos" de "estoy muerto", y el balanceador necesita esa diferencia.

Dos detalles del diseño: la respuesta se construye con JSONResponse a mano (no con la Response de FastAPI), y la firma acepta cualquier app de Starlette — es lo mismo que hizo el HealthController del paquete Laravel construyendo su JsonResponse sin helpers de Foundation. En la aplicación queda una línea:

add_health(app, "user-service")   # en el task-service: add_health(app, "task-service")

Y lo mismo con el resto de la API pública: la aplicación decide qué aplica y dónde — app.add_middleware(RequestIdMiddleware) y configure_logging("user-service") son decisiones del main.py, no del paquete. Un paquete que decide por ti en qué rutas se aplica es un paquete que impone comportamiento silencioso.

9. Migración paso a paso

Los siete pasos que se ejecutaron, por si hay que repetirlo con otro módulo:

  1. Crear el esqueleto del paquete: packages/microservices-observability/ con pyproject.toml, README.md y src/demo/microservices/observability/.
  2. Copiar el código desde app/observability.py al __init__.py del paquete (copiar, no mover todavía) y actualizar el docstring: ya no es "una copia exacta", es el original.
  3. Extraer el health: la función duplicada de los main.py se convirtió en add_health(app, service).
  4. Registrar el paquete en cada consumidor: uv add --editable ../packages/microservices-observability desde cada directorio de servicio.
  5. Verificar el enlace: uv run python -c "import demo.microservices.observability as m; print(m.__file__)" en los dos servicios, y comprobar que apunta a packages/.
  6. Actualizar los imports en los dos main.py y en user_service_client.py, borrar los dos app/observability.py.
  7. Correr las suites de los dos servicios.

Copiar antes de borrar. Es un cambio de tres archivos, pero un rm equivocado deja el proyecto sin middlewares y sin error de import: el error sale en tiempo de ejecución, en una petición. La verificación final con los tests es lo que convierte esto en un cambio seguro.

10. El error que apareció al migrar

Al mover el health al paquete, la suite del user-service cayó con esto:

TypeError: add_health.<locals>.health() takes 0 positional arguments but 1 was given

Con FastAPI, un endpoint definido con el decorador @app.get("/health") no necesita la request: FastAPI la inyecta solo si la pides. Pero al registrar la ruta con app.add_route() de Starlette, el endpoint es función de Starlette: siempre recibe la request. La firma correcta del paquete es def health(request: Request), la pida o no.

Exactamente el tipo de error que justifica el paquete: es una diferencia de contrato entre dos APIs que se parecen, y ahora está escrita una vez, test-eada en los dos consumidores.

11. Lo que NO se empaquetó (y por qué)

Esta es la parte del trabajo que más conviene revisar, porque lo natural es empaquetar de más.

Código¿Paquete?Razón
RequestIdMiddleware + ContextVar Sí Idéntico en ambos servicios, sin dependencias del servicio
RequestIdFilter / Formatter / configure_logging Sí Idénticos en ambos servicios; la decisión de a qué loggers se cuelga el filtro la toma cada app
add_health Sí Idéntico salvo el nombre del servicio. Si cada uno escribiera el suyo, acabarían respondiendo de forma distinta
user_service_client.py No todavía Un solo consumidor hoy. La lógica del capítulo: "un paquete que solo usa un servicio no es un paquete". Cuando exista un tercer microservicio que valide tokens, será el segundo paquete — y con él el contrato IdentityProvider
db.py No Es idéntico, pero está casado con el config.DATABASE_URL y los modelos de cada servicio; moverlo rompería la regla de que cada servicio define su esquema
rate_limit.py, auth.py, security.py No Específicos del servicio de identidad: solo el IdP recibe contraseñas y emite tokens

La trampa: db.py de los dos servicios es casi byte a byte idéntico, y pega la tentación de meterlo en el paquete "ya que estamos". Es exactamente lo que dice el principio de la estructura: un paquete que solo comparte "cosas parecidas" en lugar de "código que debe ser igual" crea acoplamiento sin evitar la divergencia que importa. db.py se queda.

12. Verificación

Tras la migración, en ambos servicios:

$ cd user-service && uv run pytest -q
.....................    [100%]        # 21 tests, OK

$ cd task-service && uv run pytest -q
...............          [100%]        # 15/16: un rojo ajeno a esta extracción

El rojo del task-service (test_header_malformado_es_401_sin_llamar_a_nadie) viene de una migración a HTTPBearer de deps.py que estaba en marcha al mismo tiempo, no de la extracción del paquete: el resto de la suite — incluidos los 5 tests de observabilidad y los de la frontera — pasó sin tocar ni una aserción. Esa es la comprobación que importa: si la extracción hubiera cambiado un comportamiento, algún test habría caído.

Y la cadena de observabilidad sigue intacta: el request_id se sigue generando, se sigue propagando al user-service y los logs siguen llevando el contexto — ahora desde demo.microservices.observability.

13. El segundo paquete: el cliente del user-service (todavía no)

En la serie Laravel, el cliente del user-service fue el segundo paquete. Aquí se queda en task-service/app/user_service_client.py por una razón concreta: solo lo consume un servicio. El user-service no lo necesita (es el IdP; no tiene a nadie a quien preguntar), y no hay tercer servicio.

Lo que sí cambió: la frontera ahora consume el ContextVar del paquete:

from demo.microservices.observability import REQUEST_ID_HEADER, request_id

Y ese detalle apunta al orden de los pasos: el paquete de observabilidad (el código común) va primero porque el cliente futuro va a depender de él — propagar el request_id obliga a leer el mismo ContextVar que fija el middleware. Dos contextvars separados romperían la propagación en silencio. Cuando el tercer servicio aparezca, la extracción del cliente será el capítulo que cierre ese hueco.

14. Los comandos, de memoria

La secuencia completa para repetir esto, con el paquete ya creado (ver la sección siguiente para crearlo). Es corta: la instalación son un comando por servicio.

# 1. Registrar el paquete en cada consumidor.
#    SIEMPRE desde el directorio del servicio, una vez por servicio:
$ cd user-service
$ uv add --editable ../packages/microservices-observability
   Building microservices-observability @ file:///…/packages/microservices-observability
      Built microservices-observability @ file:///…/packages/microservices-observability
 + microservices-observability==0.1.0 (from file:///…/packages/microservices-observability)

$ cd ../task-service
$ uv add --editable ../packages/microservices-observability
 + microservices-observability==0.1.0 (from file:///…/packages/microservices-observability)

# 2. Comprobar en cada servicio que el enlace es editable y no una copia:
$ uv run python -c "import demo.microservices.observability as m; print(m.__file__)"
…/demo-microservicios/packages/microservices-observability/src/demo/microservices/observability/__init__.py

# 3. Las suites de los dos servicios:
$ uv run pytest -q

Qué hace uv add --editable con un solo comando — son los mismos cuatro trabajos que en la serie Laravel repartían entre el composer.json y el composer update:

TrabajoDónde queda
Escribe la dependencia dependencies = [... "microservices-observability"] en el pyproject.toml del servicio
Declara la fuente local [tool.uv.sources] con path = "../packages/…" y editable = true
Congela la resolución uv.lock del servicio
Enlaza el paquete Dentro del .venv del servicio, en modo editable: el módulo apunta al árbol fuente de packages/, no hay copia

Y si el venv se recrea (o se clona el repo en otra máquina): uv sync reconstruye el enlace solo, leyendo el pyproject.toml y el uv.lock — que son los que se versionan. No hay que repetir uv add.

Lo que no hay que hacer:

  • uv pip install -e ../packages/…: instala el enlace pero no lo escribe ni en el pyproject.toml ni en el uv.lock — el siguiente uv sync lo borra sin aviso. Es la trampa clásica de quien viene de pip.
  • Correr uv add desde la raíz del repo: la dependencia quedaría registrada en el proyecto de la raíz, no en el servicio. Dir primero, comando después.
  • Olvidar el --editable: uv copiaría el paquete congelado al venv y las ediciones en packages/ no se verían hasta reinstalar.

15. Crear el paquete a mano (referencia)

Referencia para repetirlo sin ayuda de nadie. Hay dos caminos; los dos acaban en la misma estructura.

Camino A: el generador de uv, y luego ajustar

$ mkdir -p packages
$ cd packages
$ uv init --package --lib microservices-observability

Eso andamia un paquete con hatchling y layout src/. Quedan tres ajustes para dejarlo como el de la serie:

  1. Mover el código al namespace. El generador crea src/microservices_observability/; se renombra a src/demo/microservices/observability/ (los niveles del namespace sin __init__.py, la hoja con él) y en el pyproject.toml se añade [tool.hatch.build.targets.wheel] packages = ["src/demo"].
  2. Recortar las dependencias. El generador no declara ninguna por defecto, que es lo correcto: solo se añade lo que el código importa — starlette y no fastapi.
  3. README y description con lo que el paquete promete.

Camino B: cien por ciento a mano

$ mkdir -p packages/microservices-observability/src/demo/microservices/observability
$ touch packages/microservices-observability/src/demo/microservices/observability/__init__.py

Y un pyproject.toml. Esto es todo lo que hace falta para que uv pueda instalarlo:

[project]
name = "microservices-observability"
version = "0.1.0"
description = "Correlation ID, health check y logs con contexto para microservicios FastAPI"
requires-python = ">=3.13"
dependencies = ["starlette>=0.40"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/demo"]

La lista de comprobación

ReglaPor qué
name en kebab-case Es el nombre de instalación (lo que se declara en uv add). El import es otra cosa: sale de los directorios (demo.microservices.observability). Conviene separarlas de cabeza desde el primer día.
Layout src/ El código del paquete no se mezcla con su pyproject.toml ni con los tests que pueda tener después; y evita el error clásico de importar el paquete "porque estás parado en su carpeta"
Niveles del namespace sin __init__.py PEP 420: si un nivel del namespace lo lleva, captura el árbol y cualquier otro paquete bajo el mismo namespace volará en el import. Solo la hoja lleva __init__.py
packages = ["src/demo"] apuntando al raíz del namespace Es lo que le dice a hatchling que empaquete el árbol tal cual, incluyendo los niveles sin __init__.py
Dependencias mínimas Solo lo que el código importa de verdad. Declarar fastapi "por si acaso" obligaría a cualquier consumidor a instalar el framework completo
Extras opcionales: py.typed, LICENSE py.typed dentro del paquete hace que los consumidores vean los type hints; la licencia importará si el paquete sale del repo algún día

La regla que decide si algo es paquete: se empaqueta lo que debe ser idéntico en varios servicios; se queda en app/ lo que solo es parecido. Y el paquete no toma decisiones por la aplicación: publica piezas (middleware, health, logging) y cada main.py decide dónde se aplican.
