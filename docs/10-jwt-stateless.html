JWT stateless: la clave pública en vez del salto de red

Resumen: hasta ahora, cada petición a task-service o billing-service hacia un GET /api/user al IdP para saber quién era el token. Con el token opaco no había otra forma: solo el IdP guardaba la fila. En este capítulo el IdP firma un JWT RS256, publica su clave pública en /api/jwks.json y los relying parties verifican la firma localmente. El resultado medible: con el IdP matado, una petición autenticada sigue dando 200 en ~2 ms, frente al 503 del capítulo 6.

Lo importante no es solo el JWT: es que este es el segundo contrato que aprende el paquete microservices-user-service-client sin que ningún servicio tenga que enterarse. El capítulo 6 compró un sitio único para la frontera; aquí se cobra.

Referencias de la serie Laravel: laravel/docs/08-que-se-hizo-sso.html y laravel/docs/10-jwt-stateless.html.

1. Del 08 al 10: qué se portó y qué no

El capítulo 08 de Laravel resuelve un problema muy concreto: tres aplicaciones con formulario de login, cookies y sesiones propias que no se hablan entre sí. Aquí ese problema no existe: no hay SessionMiddleware, ni cookies, ni plantillas, ni tabla users en task-service o billing-service. Ya son relying parties puros, y la regla de oro del 08 —la identidad vive solo en el IdP— la cumplimos desde el capítulo 1.

Pieza del 08¿En FastAPI?Por qué
Identidad solo en el IdPYa estabaLos RPs no tienen usuarios: solo validan tokens
Ticket SSO con sha256, TTL y un solo usoNo aportaEs el mismo primitivo que ya usa el token opaco (hash + TTL de 60 min)
Canje /api/sso/exchange por RPNoCon JWT no se guarda token por RP: no hay nada que canjear
Whitelist de redirect_uriNoNo hay navegador ni redirects que proteger
Single logout / revocaciónSí, como lecciónHoy DELETE /api/tokens borra la fila y revoca de verdad; con JWT pasa a ser un no-op. Ahí está la parte transferible

Decisión: el 08 se cuenta, no se implementa. Portarlo habría significado construir sesiones web para desmontarlas en el capítulo siguiente. Lo que sí se implementa es el 10, y se hace con el foco puesto en el paquete 2, no en el IdP.

2. La idea: dos formas de responder a la misma pregunta

La pregunta es siempre la misma: ¿quién es este token? Y hay dos caminos:

Opaco  ──> GET /api/user al IdP ──> fila en api_tokens ──> {id, name, email}
JWT    ──> firma RS256 + JWKS cacheada ──> claims ──> {id, name, email}
                     (sin salto de red por petición)

Los dos caminos conviven. No hay un interruptor global que rompa tokens antiguos: el dispatcher decide por la forma del token — tres segmentos separados por puntos significa JWT; cualquier otra cosa sigue por la carretera del capítulo 2. Así un mismo proceso puede atender tokens de los dos modos mientras se migran los clientes.

En el IdP, TOKEN_MODE decide qué se emite:

TOKEN_MODE=opaque   (default) → token de 64 chars, una fila en api_tokens
TOKEN_MODE=jwt                → JWT de 3 segmentos, CERO filas en api_tokens

El default importa: los 21 tests anteriores siguen pasando sin tocar nada, y eso es lo que permite distinguir un rojo nuevo de uno viejo mientras se implementa.

3. Los comandos UV de este capítulo

Dos dependencias nuevas, pyjwt (firmar/verificar) y cryptography (generar RSA y cargar las claves). UV resolvió pyjwt 2.15.1 y cryptography 50.0.2. Los comandos ejecutados, desde el directorio de cada proyecto —no hay workspace—:

# 1. IdP: firma RS256 y lectura de claves PEM
cd user-service
uv add 'pyjwt>=2.8' 'cryptography>42'

# 2. Paquete 2: el verificador de los RPs
cd ../packages/microservices-user-service-client
uv add 'pyjwt>=2.8' 'cryptography>42'

# 3. Generar el par RSA del IdP (una vez; la privada queda 0600)
cd ../../user-service
uv run python -m app.jwt_keys

# 4. Tests de los tres proyectos, cada uno desde su directorio
cd user-service     && uv run pytest        # 32/32
cd ../task-service  && uv run pytest        # 27/27
cd ../billing-service && uv run pytest      # 19/19

# 5. Servicios en modo JWT (el IdP con las variables de clave)
uv run uvicorn app.main:app --port 8000                    # user-service, TOKEN_MODE=jwt
uv run uvicorn app.main:app --port 8001                    # task-service
uv run uvicorn app.main:app --port 8002                    # billing-service

El resultado en los pyproject.toml es una línea en dependencies por servicio/paquete, y el uv.lock de cada proyecto se actualizó por separado. En el paquete 2, uv add añadió además sus dependencias transitivas (cffi, pycparser); los servicios que lo consumen en modo editable recibieron el paquete actualizado al siguiente uv run, sin uv sync manual.

Regla del repo: los comandos uv siempre desde el directorio del servicio o del paquete. Un uv run lanzado desde la raíz usa otro entorno y hace creer que el cambio "no funcionó".

4. El IdP: firmar y publicar

4.1. Las claves

uv run python -m app.jwt_keys genera un par RSA de 2048 bits con cryptography. La privada se escribe con permisos 0600 y la pública como PEM; el kid se deriva del hash sha256 del material público (16 hex), así que la misma clave siempre tiene el mismo identificador. Si el par ya existe, el comando se niega a sobrescribirlo: regenerarlo invalidaría todos los JWT vivos.

$ uv run python -m app.jwt_keys
Par RSA generado. kid=e61a3fe6ab452f38
Privada: jwt_keys/private.pem (0600) · Pública: jwt_keys/public.pem

Las rutas se configuran con JWT_PRIVATE_KEY_PATH y JWT_PUBLIC_KEY_PATH; en el E2E se apuntaron a un directorio temporal para no dejar claves en el repo. app/config.py añade, además de TOKEN_MODE, JWT_TTL_MINUTES=15 y JWT_ISSUER=user-service.

4.2. El emisor y la JWKS

app/jwt_issuer.py centraliza cuatro operaciones: cargar la privada, cargar la pública, derivar el kid y convertir los números de la clave a base64url sin padding para la JWK. Los claims del token:

{"iss": "user-service", "sub": "1", "name": "Ana Torres",
 "email": "ana.torres@example.com", "iat": ..., "exp": ...,
 "jti": "<32 hex>", "device_name": "api-token"}

GET /api/jwks.json es público y responde con una única clave:

{"keys": [{"kty": "RSA", "use": "sig", "alg": "RS256",
           "kid": "e61a3fe6ab452f38", "n": "...", "e": "AQAB"}]}

Sin claves en disco, tanto el login en modo JWT como el endpoint de JWKS responden 503 con el comando para generarlas. Fallo de configuración, no de identidad: nunca se disfraza de 401.

4.3. Emisión, /api/user y revocación

issue_access_token() es la fachada que separa los dos modos: en JWT firma y no toca la BD; en opaco ejecuta el código de siempre (hash sha256 en api_tokens, token crudo una sola vez). La respuesta TokenIssued es idéntica en los dos casos, y el rate limit del login sigue colgado de la ruta.

app/auth.py aplica el mismo dispatch por forma que el paquete: si el token tiene dos puntos, se verifica localmente con la clave pública y se busca al usuario por sub; si no, se busca su fila. Por eso el propio IdP acepta su JWT en GET /api/user sin llamarse a sí mismo.

DELETE /api/tokens valida el token y:

Modo del tokenRespuestaEfecto
Opaco204Borra la fila: revocación real e inmediata
JWT204No-op: no hay fila; el token sigue vivo hasta exp. Log API token revoke skipped

El log de emisión cambia de campo: en lugar del nombre del dispositivo lleva {"mode": "jwt", "jti": "…"}. El jti permite correlacionar el token con el login sin escribir nunca el token crudo en los logs. De paso se quitó un "API token issued" espurio que whoami escribía en cada GET /api/user.

5. El paquete 2: verificar sin red

Tres archivos nuevos en packages/microservices-user-service-client/src/demo/microservices/user_service_client/:

ArchivoQué hace
jwks.py JwkKeyStore: baja la JWKS, la cachea en memoria 1 h (USER_SERVICE_JWKS_CACHE_TTL), convierte cada JWK a clave RSA con RSAAlgorithm.from_jwk, y hace un solo refetch si aparece un kid desconocido. Un kid forjado no puede martillear el IdP.
jwt_verifier.py verify(token, store): exige cabecera RS256 con kid, valida firma, iss=user-service, exp con leeway=10 y los claims obligatorios. Devuelve el dict de identidad o lanza. Separa identidad inválida de JWKS no disponible.
__init__.py verify_token pasa a ser dispatcher: dos puntos → verificación local; cualquier otro token → _verify_opaque, que es el código del capítulo 2 sin cambiar ni un mensaje de error. 
def verify_token(token: str) -> dict[str, Any]:
    if token.count(".") != 2:
        return _verify_opaque(token)
    try:
        return verify_jwt(token, jwks)
    except JwksUnavailable as exc:
        # Sin clave pública no se puede verificar: 503, NUNCA 401.
        ...
    except (UnknownKid, jwt.PyJWTError, ValueError, TypeError) as exc:
        # Identidad inválida: 401 SIN llamar al IdP.
        ...

El store es uno por proceso, como el limitador de login del IdP: la JWKS se baja una vez y la comparten todas las peticiones que atiende ese worker. Con N réplicas, cada una cachea por su lado; el capítulo 9 de resiliencia seguirá teniendo sentido para el camino opaco, que no desaparece.

El argumento del capítulo 6, cobrado: ni deps.py, ni routes_tasks.py, ni routes_bills.py, ni sus tests de negocio se tocaron en este capítulo. Solo cambiaron los pyproject.toml y el paquete. El contrato verify_token(token) -> {"id", "name", "email"} es la frontera que hace posible eso — el equivalente de IdentityProvider en la serie Laravel.

9. Los precios del stateless

  • Revocación: sin filas no hay invalidación antes de exp. TTL de 15 minutos y DELETE no-op. Una denylist por jti la haría stateful otra vez: se decidió no pagar ese precio y decirlo claro.
  • Arranque en frío: JWKS sin caché + IdP caído = imposible de verificar. Se falla cerrado con 503; jamás se degrada a 401, porque un 401 sugeriría que el cliente tiene la culpa.
  • La traza cambia de camino: en modo JWT no hay GET /api/user, así que X-Request-Id ya no cruza al IdP. El ContextVar sigue dando contexto a los logs locales (el warning de JWKS caída lleva su request_id), pero la petición de autenticación no sale del RP. Es una consecuencia de eliminar el salto de red, no una regresión.
  • Rotación: regenerar el par invalida todos los JWT vivos. Los RPs refetch solos al ver otro kid; un kid desconocido que no aparece se rechaza sin repetir la descarga.
  • Seguridad: RS256, nunca HS256 — con una clave simétrica cualquier RP podría fabricar tokens. iss explícito, leeway de 10 s, jti para correlacionar sin exponer el token, y privada con permisos 0600 fuera del repo.
